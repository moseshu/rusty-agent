## 3. 核心协议

### 3.1 `BaseSandboxClient`（`session/sandbox_client.py`）

泛型 `Generic[ClientOptionsT]`，类属性两个：`backend_id: str`、`supports_default_options: bool = False`。

公共方法五个：

| 方法 | 形态 | 契约要点 |
| --- | --- | --- |
| `create(...)` | async | 建新 session；建前走 `_validate_manifest_for_create` |
| `resume(...)` | async | 从 state 恢复 |
| `delete(session)` | async | 返回 `SandboxSession`，**不是 None** |
| `serialize_session_state(state)` | sync | → `dict[str, object]` |
| `deserialize_session_state(payload)` | sync | ← `dict[str, object]` |

内部三处必须一起移植的行为：`_wrap_session`（instrumentation 包装）、`_resolve_dependencies`、`_serialize/_deserialize_session_state_payload`（子类可覆盖的序列化钩子）。

`BaseSandboxClientOptions` 是 **pydantic 模型 ＋ 子类注册表判别联合**：
- `type: str` 是判别字段；
- `_subclass_registry: ClassVar[dict[str, ...]]` 在 `__pydantic_init_subclass__` 时登记；
- `parse(payload)` 按 `type` 找回具体 options 类；
- `_serialize_always_include_type` 保证序列化**永远带 `type`**。

> Rust 落点：这是 serde 的 `#[serde(tag = "type")]` 内部标记枚举＋注册表二选一。注册表在 Rust 里要么用 `inventory`/`linkme` 静态注册，要么由宿主显式装配。**建议显式装配**（宿主把支持的后端登记进一张表），因为链接期注册会让「支持哪些后端」随 feature 组合漂移。

### 3.2 `BaseSandboxSession` / `SandboxSession`

两层：`BaseSandboxSession`（`abc.ABC`，后端实现它）与 `SandboxSession`（在其上加事件、trace、限流、路径校验的**装饰层**）。只有一个 `@abc.abstractmethod`：`_exec_internal`。其余都是带默认实现的模板方法钩子。

生命周期以 `BaseSandboxSession` 的实际控制流为准，不能简化为无条件串行链：

| 操作 | 成功路径 | 分支与失败语义 |
| --- | --- | --- |
| `start()` | 先校验 mount credential boundaries；进入 try 后依次 `_ensure_backend_started`、记录 `workspace_root_ready`、`_probe_workspace_root_for_preserved_resume`、`_prepare_backend_workspace`、`_ensure_runtime_helpers`、`_start_workspace`；成功后 `_after_start`，最后设 `workspace_root_ready=True` | **探测先于准备**，避免把新建目录当成恢复证据。try 内 `Exception` 才走 `_after_start_failed` 与 `_wrap_start_error`；前置校验和 try 外 `_after_start` 的失败不经过该分支。不得擅自把取消异常与普通异常归为同一种捕获。 |
| `_start_workspace()` | 再校验挂载边界，然后按 snapshot 与 workspace 是否保留选择路径 | snapshot 可恢复且 fingerprint/manifest 允许复用：只重建 ephemeral；可恢复但不能复用：恢复 snapshot 再重建 ephemeral；无可恢复 snapshot 但工作区确认保留：只重建 ephemeral；其余：完整物化 manifest。`_restore_snapshot_and_reapply_ephemeral_on_resume` **不是每次 start 必经步骤**。 |
| `stop()` | 前置挂载校验后 `_before_stop`（默认终止 PTY）→ `_persist_snapshot` | try 内失败走 `_wrap_stop_error`；进入 try 后 `_after_stop` 在 **finally** 执行，持久化失败也执行。前置校验失败尚未进入该 finally。stop 是持久化阶段，不等于关闭后端。 |
| `shutdown()` | `_before_shutdown`（默认终止 PTY）→ `_shutdown_backend` → `_after_shutdown` | 顺序 await，没有把后两步放 finally；前一步失败会跳过后续。 |
| 直接 `aclose()` | 取得关闭锁后 `_aclose_impl`：pre-stop hooks → 条件 stop → shutdown → finally 关闭 dependencies；不自动调用 client.delete | hooks 失败记录首个错误，跳过 stop，仍尝试 shutdown；**stop 失败时跳过 shutdown**，但仍关闭 dependencies 并抛首个记录错误。重复关闭／hooks 失败粘性按源码和测试移植，不另作幂等假设。 |
| Runner-owned cleanup | 由 `_SandboxSessionResources.cleanup` 执行，不能直接以 `aclose` 替代 | borrowed 直接返回；owned 受锁与 `_cleaned` 保护：hooks 失败跳过 stop；stop 失败仍尝试 shutdown；finally 尝试符合条件的 client.delete，最后关闭 dependencies；保留首个错误。 |

`SandboxSession` 装饰层转发到 inner；生命周期错误的挂载信息脱敏也必须保留。上面两种关闭入口的差别是固定基线的事实，若将来跟随上游修复，应单独升级基线，不能在移植时悄悄统一。

**能力探测**两个：`supports_pty()`、`supports_docker_volume_mounts()`——工具装配直接读它们。

对外操作面：

| 族 | 方法 |
| --- | --- |
| 执行 | `exec(*command, timeout, shell=True, user)` → `ExecResult`；内部 `_prepare_exec_command` → `_exec_internal` |
| PTY | `pty_exec_start`、`pty_write_stdin`、`pty_terminate_all` |
| 文件 | `ls`、`rm`、`mkdir`、`read`、`write`、`normalize_path`、`_validate_path_access` |
| 归档 | `persist_workspace()` → `io.IOBase`、`hydrate_workspace(data)` |
| 端口 | `resolve_exposed_port(port)` → `ExposedPortEndpoint` |
| Manifest | `apply_manifest(only_ephemeral=False)` → `MaterializationResult` |
| 状态 | `running()`、`state` property |
| 依赖 | `dependencies()`、`set_dependencies()`、`register_pre_stop_hook()` |

`exec` 的默认 `shell=True` 语义写在 docstring 里：**前缀 `sh -lc`**；传 list 可换前缀。这是 `login` 语义的真正来源。

### 3.3 `SandboxSessionState`（`session/sandbox_session_state.py`）

公共字段八个，同样用 `type` 判别 ＋ `_subclass_registry`：

```
type: str
session_id: uuid.UUID          # 默认 uuid4
snapshot: SerializeAsAny[SnapshotBase]
manifest: Manifest
exposed_ports: tuple[int, ...] # 默认空
snapshot_fingerprint: str | None
snapshot_fingerprint_version: str | None
workspace_root_ready: bool     # 默认 False
```

三个私有属性影响恢复安全：`_path_grants_require_rebind`、`_mount_authority_redacted`、`_mount_authority_rebound`。**恢复时挂载凭据要重新绑定而不是从 state 里读回**——这条直接决定序列化格式，必须移植，不能简化。

### 3.4 `types.py`

| 类型 | 形态 | 要点 |
| --- | --- | --- |
| `User` | `{name: str}` | 按 name 做 hash/eq |
| `Group` | `{name, users: list[User]}` | 按 name 做 hash/eq |
| `Permissions` | `{owner=0o7, group=0, other=0, directory=False}` | `to_mode` / `from_mode` / `from_str`；`from_str` 要处理 `ls` 的 ACL/xattr/SELinux 尾标 `+ @ .`，并认 `s/S/t/T` |
| `FileMode` | IntEnum | `ALL=0o7, NONE=0, READ=4, WRITE=2, EXEC=1` |
| `ExecResult` | `{stdout: bytes, stderr: bytes, exit_code: int}` ＋ `ok()` | **stdout/stderr 是分开的 bytes** |
| `ExposedPortEndpoint` | frozen `{host, port, tls=False, query=""}` ＋ `url_for(scheme)` | 只认 `http`/`ws`；IPv6 加方括号；默认端口省略 |

> `Permissions.owner` 默认 `0o7`（rwx）而 group/other 为 0——**默认是 0700 语义**，与 Rusty `RunTempDir` 的 `0o700` 巧合一致，但那是两回事，不能互相引证。

### 3.6 当前 Rust 增量的验收边界（2026-09-16）

截至首个增量，`ra-core::sandbox` 交付值类型、错误码与错误载荷，**不代表 R8-P1 全部完成**。Client/Session/State、具体 options/state 注册、依赖容器、生命周期装饰层和恢复授权重绑定仍待移植，不能用本增量的测试替代这些验收。后续注册机制增量见 §3.7。

本次审核修复：

- `Permissions` 反序列化省略字段时复用 `Default`（0700、非目录）；`ExposedPortEndpoint` 的 TLS/query 同样保留上游缺省值。
- `owner_can/group_can/others_can` 接受 `FileMode` 或 `u32` 掩码；位或组合返回 `u32`，支持读写、读执行等组合。Rust 的数值掩码使用 `0o6_u32` 等显式类型；builder 消费并返回值，适配 Rust 所有权，不模拟 Python 可变对象别名。
- Python 异常继承用 `ErrorCode` + `SandboxErrorDetails` 表达；`exec_nonzero/exec_timeout/exec_transport/pty_session_not_found` 保留类型化载荷，原始输出字节与供人阅读的有损 UTF-8 context 分开保存。context 覆盖不修改类型化载荷。
- 端口及常用 workspace 错误提供具名构造入口。通用 `SandboxError::new` 仍是低层入口；其余上游异常的具名构造与调用点迁移未宣称全部完成。
- Rust builder 的重试属性在读取时回退到直接 sandbox cause，因而通过 `with_cause` 或 `with_sandbox_cause` 设置原因一致，显式 `Some(bool)` 优先；`None` 表示继承原因或保持未知。此做法适配 Rust 分步构造，避免 setter 调用顺序改变最终语义。

验证：`cargo test --manifest-path tests/it-core/Cargo.toml --test sandbox_contract`，35 项通过；`cargo clippy -p ra-core -- -D warnings` 通过。

### 3.7 注册机制与 Snapshot 值对象增量（2026-09-17）

新增的是显式 `TypeRegistry`、原始 `DiscriminatedPayload` 与最小 `Snapshot` 值对象。`client_options_kind/session_state_kind/snapshot_kind` 仅区分注册表家族和错误策略；不是具体 options/state 的实现，也没有实现挂载授权清理或重绑定。`BaseSandboxClient`、`BaseSandboxSession`、`Manifest`、`SandboxSessionState` 及 state 往返仍未交付；Snapshot 的 IO 行为仍归 P7。

审核修复与 Rust 表达差异：

- 扩展字段不能覆盖 `type`；与 Snapshot 的 `id` 一样，写入保留键的 builder 调用不修改值。序列化最后写入权威 discriminator，normalizer 也不能改成另一种类型。
- state 家族的未知类型和校验失败错误不保留原始 discriminator、验证器 reason 或 source；`Display` 和 `Debug` 都不携带这些敏感数据。非脱敏家族仍保留诊断详情。
- `DiscriminatedPayload` 明确是可构造、可反序列化的未校验数据。`readmit` 重新执行注册验证器，不能照搬上游“已构造的具体模型直接返回”的捷径，因为该原始载荷没有同等的构造校验保证。
- `Snapshot` 保留 `Serialize`，移除无需注册表的 `Deserialize` / `TryFrom<Value>`，`from_payload` 改为私有。持久化恢复先读为 JSON，再调用 `Snapshot::parse(&registry, &value)`，确保未知类型拒绝和具体类型 normalizer 都生效。`new/with_field` 用于受信任的后端配置构造，不是持久化恢复入口。这是显式注册表不能通过普通 serde `Deserialize` 隐式传入所需的适配，没有引入全局注册表。

回归覆盖：保留键覆盖、state 错误的 Display/Debug/source 脱敏、构造／反序列化／修改后 readmit 的验证、接收方 normalizer、Snapshot 经注册表恢复与往返、normalizer 改换类型的拒绝；另有编译失败文档测试防止恢复无注册表的 Snapshot 反序列化入口。

| `resolve_workspace_path` | 同名（`allow_absolute_within_root=False` 分支） | 按写法校验：`pkg/../pkg/file` 即便归一化后仍在工作区内也拒绝，与上游一致 |

**线格式已用上游实测逐项核对**（`Manifest.model_dump(mode="json")` 与 `describe()`）：条目平铺字段与默认权限 0755（目录型 `directory=true`）、`git_repo` 的 `host/ref/repo/subpath`、`local_dir` 的 `src: null`、`file.content` 为 UTF-8 字符串且非 UTF-8 上游同样报错；挂载的 `mount_path/read_only/mount_strategy`、`pattern.options` 嵌套、`docker_volume.driver_options`；环境的 `{"value": {...}}` 包一层与 `EnvEntry` 的三字段；`describe(depth=1/2/None)` 的树形输出逐行相同。

Rust 表达差异（每条都注明必要性）：

- **`WorkspacePathPolicy` 只移植 POSIX（远端）那一半。** 上游同一个类里还有一条跟随宿主符号链接的路径（`resolve_symlinks`、`root_is_existing_host_path`、`sandbox_path_grant_host_path` 的 `resolve()`），那需要读真实文件系统；`ra-core` 不做 IO 是 §8 的分层裁决。**词法检查不能替代它**：工作区内的符号链接可以指向工作区外，只有解析型检查能发现。该半边随 P3 的 unix-local 落地。
- **`PosixPath` 在构造时按 `PurePosixPath` 的规则整理拼写**：合并重复分隔符、丢掉单独的 `.`、去掉尾部分隔符，保留恰好两个前导斜杠，**但不动 `..`**。不整理会让 `resolve_workspace_path("/w", "./README.md")` 产出 `/w/./README.md`、`anchor("./plot.png")` 产出 `tasks/a/./plot.png`，与上游不一致。解析 `..` 是 `normalized()`，仍与构造分开。
- **`Manifest` 去掉 `Deserialize`，改用 `Manifest::parse(&registry, &value)`。** 条目类型是开放家族，普通 serde 反序列化传不进注册表。与 §3.7 的 `Snapshot` 同一处理。`Environment::parse` 另收一张 env value 注册表，两张表分开是因为家族本来就是两个。
- **`Dir.children` 与 `Manifest.entries` 用 `BTreeMap`（按名排序），不是插入序。** `iter_entries` 仍是前序。上游的插入序不被任何语义依赖（`describe` 自己排序、`ephemeral_entry_paths` 是集合、物化是并发的）。
- **`MountPattern` 是闭合枚举，`MountStrategy` 与 `MountProvider` 开放。** 上游 `pattern` 字段就是四选一的判别联合（未注册的工具直接拒），而 `MountStrategyBase` 和 `BaseEntry` 有子类注册表。三者的开闭跟着上游走。
- **挂载权限位不生效，Rust 直接固定而不告警。** 上游 `warnings.warn` 后覆盖；没有任何值会被兑现，日志只是把一次无效配置写进流水。文档写明访问控制在 provider 侧配置。
- **`Environment::resolve` 的兄弟取消由 combinator 提供。** 上游需要专门的 `gather_with_cancel`，因为 `asyncio.gather` 出错即返回、剩余任务仍在跑；Rust 里 `try_join_all` 出错即被丢弃，丢弃 future 就是取消。语义相同，不另写并发原语。
- **`GitRepo` 的 `ref` 字段在 Rust 叫 `reference`**（`ref` 是关键字），线上仍写 `ref`。
- **`EntryContent::Mount` 装箱**：挂载带着整套 provider 凭据字段，不装箱会让每个条目都按最大的挂载算大小。
- **截断的定点搜索加了 8 轮上限。** 标记文本里写着被丢掉多少字符，它自己的长度又取决于那个数字；上游的循环没有出口，相差一位数字的两个长度可以互相换位。到上限就采用最后一次测量。
- **不做截断日志。** 上游 `logger.warning`；截断本身已经写在输出里（而且是给模型看的那句），比日志更有用，`ra-core` 也不引入日志副作用。
- `PathGrantError` 新增 `NotAGrant`／`PathMissing`／`FieldType`：上游由 pydantic 的必填与类型校验报出，Rust 手写读取需要自己命名这三种；其余六条错误文案与上游逐字相同。
- **渲染省略空集合**（entries／environment／users／groups／extra_path_grants）。上游一律写出空集合。两边所有字段都有默认值，互相都读得进；差别只在空 manifest 写多少字节。此为前一批已有的取舍，本批沿用未改。

**本批未移植、明确留给后续的**：

- 挂载生命周期本身——`MountPattern.apply/unapply`、rclone 配置合成、`teardown_for_snapshot`／`restore_after_snapshot`、`InContainerMountAdapter`／`DockerVolumeMountAdapter`、`build_docker_volume_driver_config` 的选项拼装。都要一个活的 session 去执行命令，归 P3/P7/P8 与服务 crate。
- `validate_mount_activation_credential_boundary`：激活时的凭据边界检查，需要活 session、`provider_backend_id` 和解析后的挂载路径。本批交付的分类表与 `acknowledges_*` 查询是它的输入。
- `_mount_security.py` 的错误脱敏装饰器（`redact_mount_error_data` 等）：包的是 async 生命周期调用，同上。
- `_mount_security.py` 的「可信类来源」判定（`_mount_entry_class_is_trusted` 等）：靠 Python 的 `__module__`/`__qualname__` 比对防止导入顺序伪装，Rust 没有等价问题——内建注册表里的类型就是内建的。
- `gather_in_order` 与 `SandboxConcurrencyLimits`：物化的并发限流，归执行方与 P4 的 run config。
- `_coerce_manifest` 的「以映射形式提供的 manifest 不得声明 `extra_path_grants`」：run config 强制点，随 P4。
- 会话侧的 manifest application／mount lifecycle 顺序（`_apply_entry_batch` 等）：需要服务 crate。

## 4. 运行集成

### 4.1 `SandboxRunConfig`（`run_config.py`）—— 九个字段

| 字段 | 默认 | 语义 |
| --- | --- | --- |
| `client` | None | 建/恢复 session 的客户端 |
| `options` | None | 建新 session 时的客户端特定选项 |
| `session` | None | **外部 live session 覆盖**（本进程内） |
| `session_state` | None | 不用 `RunState` 时的显式恢复来源 |
| `manifest` | None | 建新 session 的 manifest 覆盖 |
| `snapshot` | None | 建新 session 用的快照 |
| `concurrency_limits` | `SandboxConcurrencyLimits()` | 物化并发 |
| `archive_limits` | **None** | None＝不施加 SDK 归档限制；要默认值须显式传 `SandboxArchiveLimits()` |
| `cwd` | None | **模型可见的工作目录**，相对 workspace root |

`cwd` 的语义边界写得很死，必须原样移植：它**只改相对路径解析**，不限制 run、不阻止访问会话策略允许的其他路径、不改 `Manifest.root`、不改 `BaseSandboxSession` 的直接路径行为。内建的 `exec_command` / `view_image` / `apply_patch` 从它解析相对路径；自定义能力必须自己应用绑定的 `SandboxWorkspaceScope`。校验时目录必须存在且对配置用户可访问；新建 session 时 runner **先物化 manifest 再校验 cwd**。

两个限额类型：
- `SandboxConcurrencyLimits{manifest_entries, local_dir_files}`
- `SandboxArchiveLimits{max_input_bytes, max_extracted_bytes, max_members}`，`__post_init__` 即校验，全都 `>= 1` 或 None。

### 4.3 runtime 三件套

| 模块 | 职责 |
| --- | --- |
| `runtime.py::SandboxRuntime` | 面向 Runner 的门面：`enabled`、`current_session`、`prepare_agent`、`cleanup`、`apply_result_metadata`、`assert_agent_supported`，以及 memory 入队两个口子 |
| `runtime_agent_preparation.py` | 纯函数层：`clone_capabilities`、`prepare_sandbox_agent`、`prepare_sandbox_input`、`build_sandbox_instructions`、`resolve_instructions`、`resolve_sandbox_model_name`、`get_default_sandbox_instructions` |
| `runtime_session_manager.py::SandboxRuntimeSessionManager` | session 的建/恢复/清理与所有权：`acquire_agent`、`ensure_session`、`serialize_resume_state`、`cleanup`、`_create_resources` |

**所有权是这层的核心裁决**，`_SandboxSessionResources` 持 `owns_session: bool`：
- 外部传入的 live session → `owns_session=False`，资源 `cleanup` 直接返回，不停不删；`ensure_started` 才检查 `running()`，已运行则不重复 start，未运行则启动。manifest 的有限更新发生在资源准备阶段，不是 cleanup；
- client 创建或恢复出来的 → `owns_session=True`，由本层负责收尾。

还维护**按 agent 的资源与恢复身份**（`_resume_agent_base_key`、`_resume_state_payload_for_agent`），即一个 run 里多个 agent 各自有自己的 session 与恢复条目。

> 这一条直接否掉旧 R8-10 的「一个 run 一个容器、run 结束一律删」。

**选择优先级**（`_create_resources`）：先取显式 live `session`，此分支不创建／恢复；否则先取 `session_state`，若 `_resume_state_payload_for_agent` 返回当前 agent 对应的 RunState payload，则反序列化并覆盖显式 state，再标记持久化授权；有有效 state 则 resume，否则 create。不能把“整个 RunState 存在”当作“当前 agent 有可恢复条目”。fresh create 才检查 options 必填条件，允许默认 options 的 client 除外；resume 不走 fresh create 的 manifest/options 路径。live session 的 manifest 更新与 resume 的授权重绑定分别处理。

**运行资源清理**：按 agent 逐个尝试清理，即使前一个失败也继续处理其余；仅全部成功后序列化新的 resume state；最后清空运行内资源表并释放 agent guard。结果层对 cleanup 失败如何处理另按普通／流式路径测试，不能把资源 cleanup 抛错直接等同于整次成功结果被改成失败。

## 5. `Capability` 契约（`capabilities/capability.py`）

pydantic 模型，字段 `type`、`session`、`run_as`、`workspace_scope`（后三者 `exclude=True`，不进序列化）。

绑定三步：`bind(session)`、`bind_run_as(user)`、`bind_workspace_scope(scope)`。
克隆：`clone()` 逐字段深拷，但对 session/scope/锁/工具对象**故意不拷**（`_clone_capability_value` 白名单）。

六个可覆盖点：

| 方法 | 默认 | 用途 |
| --- | --- | --- |
| `required_capability_types()` | `set()` | 声明必须共存的能力 |
| `tools()` | `[]` | 贡献模型可见工具 |
| `process_manifest(manifest)` | 原样 | 改 manifest |
| `instructions(manifest)` | None | 追加确定性指令片段 |
| `sampling_params(params)` | `{}` | 追加模型请求参数 |
| `process_context(context)` | 原样 | 采样前改模型输入 |

默认集 `Capabilities.default()` = `[Filesystem(), Shell(), Compaction()]`。
- `Filesystem.tools()` → `[view_image, apply_patch]`
- `Shell.tools()` → `[exec_command]`，**仅当 `session.supports_pty()` 才追加 `write_stdin`**

## 8. Rust 模块与依赖落点（裁决）

保留 `xtask/src/layering.rs::ALLOWED_INTERNAL_DEPS` 的 `ra-runtime → ra-core` 约束。撤回 runtime 直接依赖同时包含后端的 `ra-sandbox` 提案；协议与具体后端分开，不能通过允许一条反向依赖把 exec、tools 和 Docker 间接带进运行内核。

| 落点 | 内部依赖／消费者 | 职责 |
| --- | --- | --- |
| `ra-core::sandbox`（新增模块） | 不增加内部 crate 依赖；由 runtime、工具和后端消费 | 上游中立的 client/session/capability 协议与共享值、错误、manifest/state 表达、snapshot/dependency 接口。runtime 需要的 SandboxAgent 配置使用组合表达；options/state 的后端扩展通过显式注册与类型擦除传递，不能用封闭的内置后端枚举堵住第三方 client。具体 Docker 字段和 IO 实现不放这里。 |
| `ra-sandbox`（拟新增服务 crate） | `ra-core`、`ra-exec`、`ra-tools`；产品装配层消费 | session 共用生命周期实现与装饰层、物化／snapshot／sinks 的具体 IO、Unix-local/Docker client，以及默认 capabilities 的具体实现。默认能力通过 ra-tools 创建绑定 session 的工具；对外提供其共享协议实现。 |
| `ra-tools::sandbox` | 新的 session 工具只依赖 `ra-core::sandbox` 协议；现有 exec/patch 依赖保留 | exec/write_stdin/patch/view_image 的上游工具形态与绑定；不依赖 ra-sandbox，避免 `ra-sandbox → ra-tools → ra-sandbox` 环。 |
| `ra-runtime` | **仍只依赖 ra-core** | RunConfig 的 sandbox 配置引用核心协议；运行资源选择、按 agent 的身份与 owned/borrowed、preparation/cleanup 调用注入的 client/session/capability。不能直接构造具体后端或工具。 |
| 产品／SDK 装配层 | 可依赖 ra-runtime、ra-sandbox；coding 产品继续依赖 ra-tools | 构造并注入客户端及默认 capability 实现、snapshot 工厂、后端注册表；提供构建 SandboxAgent 的便利入口，保持上游默认集与配置语义，不要求模型调用者手工凑三种能力。已有更严格配置单独选择。 |

**实际调用链**：装配层构造具体 client 与 capability 实例 → 经核心协议放进 sandbox agent/run 配置 → runtime 调用 client.create/resume 或使用 borrowed session → capability 绑定同一 session，产出核心 Tool 协议对象 → runtime 通过既有派发调用工具 → 工具调用 session 协议 → 后端执行。runtime 不需要知道实现在哪个 crate。

**Compaction 等跨章能力**：其共享协议先登记在核心，具体能力由服务层装配已有机制；需要其他服务依赖时在对应任务核对现有允许方向并补精确边，不允许反向依赖 runtime。未核对的实现细节仍列 §11，不据此另建 compaction 引擎。

**注册方式确定为宿主显式装配**；装配入口自动登记选用的内置实现，第三方实现可追加。保留上游类型判别、未知类型与重复登记错误，Rust 不照搬 Python 导入时副作用。P1 实现时同步登记新 crate 分层与允许边，必须验证无环和 runtime 仍仅依赖 core。本次仅裁决文档，不修改代码或放宽现有门禁。
