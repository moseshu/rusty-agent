## 3. 核心协议

### 3.1 `BaseSandboxClient`（`session/sandbox_client.py`）

泛型 `Generic[ClientOptionsT]`，类属性两个：`backend_id: str`、`supports_default_options: bool = False`。

公共方法五个：

| 方法 | 形态 | 契约要点 |
| --- | --- | --- |
| `create(...)` | async | 建新 session；建前走 `_validate_manifest_for_create` |
| `resume(...)` | async | 从 state 恢复 |
| `delete(session)` | async | 返回 `SandboxSession`，**不是 None** |
| `serialize_session_state(state)` | sync | → `dict[str, object]` |
| `deserialize_session_state(payload)` | sync | ← `dict[str, object]` |

内部三处必须一起移植的行为：`_wrap_session`（instrumentation 包装）、`_resolve_dependencies`、`_serialize/_deserialize_session_state_payload`（子类可覆盖的序列化钩子）。

`BaseSandboxClientOptions` 是 **pydantic 模型 ＋ 子类注册表判别联合**：
- `type: str` 是判别字段；
- `_subclass_registry: ClassVar[dict[str, ...]]` 在 `__pydantic_init_subclass__` 时登记；
- `parse(payload)` 按 `type` 找回具体 options 类；
- `_serialize_always_include_type` 保证序列化**永远带 `type`**。

> Rust 落点：这是 serde 的 `#[serde(tag = "type")]` 内部标记枚举＋注册表二选一。注册表在 Rust 里要么用 `inventory`/`linkme` 静态注册，要么由宿主显式装配。**建议显式装配**（宿主把支持的后端登记进一张表），因为链接期注册会让「支持哪些后端」随 feature 组合漂移。

### 3.2 `BaseSandboxSession` / `SandboxSession`

两层：`BaseSandboxSession`（`abc.ABC`，后端实现它）与 `SandboxSession`（在其上加事件、trace、限流、路径校验的**装饰层**）。只有一个 `@abc.abstractmethod`：`_exec_internal`。其余都是带默认实现的模板方法钩子。

生命周期以 `BaseSandboxSession` 的实际控制流为准，不能简化为无条件串行链：

| 操作 | 成功路径 | 分支与失败语义 |
| --- | --- | --- |
| `start()` | 先校验 mount credential boundaries；进入 try 后依次 `_ensure_backend_started`、记录 `workspace_root_ready`、`_probe_workspace_root_for_preserved_resume`、`_prepare_backend_workspace`、`_ensure_runtime_helpers`、`_start_workspace`；成功后 `_after_start`，最后设 `workspace_root_ready=True` | **探测先于准备**，避免把新建目录当成恢复证据。try 内 `Exception` 才走 `_after_start_failed` 与 `_wrap_start_error`；前置校验和 try 外 `_after_start` 的失败不经过该分支。不得擅自把取消异常与普通异常归为同一种捕获。 |
| `_start_workspace()` | 再校验挂载边界，然后按 snapshot 与 workspace 是否保留选择路径 | snapshot 可恢复且 fingerprint/manifest 允许复用：只重建 ephemeral；可恢复但不能复用：恢复 snapshot 再重建 ephemeral；无可恢复 snapshot 但工作区确认保留：只重建 ephemeral；其余：完整物化 manifest。`_restore_snapshot_and_reapply_ephemeral_on_resume` **不是每次 start 必经步骤**。 |
| `stop()` | 前置挂载校验后 `_before_stop`（默认终止 PTY）→ `_persist_snapshot` | try 内失败走 `_wrap_stop_error`；进入 try 后 `_after_stop` 在 **finally** 执行，持久化失败也执行。前置校验失败尚未进入该 finally。stop 是持久化阶段，不等于关闭后端。 |
| `shutdown()` | `_before_shutdown`（默认终止 PTY）→ `_shutdown_backend` → `_after_shutdown` | 顺序 await，没有把后两步放 finally；前一步失败会跳过后续。 |
| 直接 `aclose()` | 取得关闭锁后 `_aclose_impl`：pre-stop hooks → 条件 stop → shutdown → finally 关闭 dependencies；不自动调用 client.delete | hooks 失败记录首个错误，跳过 stop，仍尝试 shutdown；**stop 失败时跳过 shutdown**，但仍关闭 dependencies 并抛首个记录错误。重复关闭／hooks 失败粘性按源码和测试移植，不另作幂等假设。 |
| Runner-owned cleanup | 由 `_SandboxSessionResources.cleanup` 执行，不能直接以 `aclose` 替代 | borrowed 直接返回；owned 受锁与 `_cleaned` 保护：hooks 失败跳过 stop；stop 失败仍尝试 shutdown；finally 尝试符合条件的 client.delete，最后关闭 dependencies；保留首个错误。 |

`SandboxSession` 装饰层转发到 inner；生命周期错误的挂载信息脱敏也必须保留。上面两种关闭入口的差别是固定基线的事实，若将来跟随上游修复，应单独升级基线，不能在移植时悄悄统一。

**能力探测**两个：`supports_pty()`、`supports_docker_volume_mounts()`——工具装配直接读它们。

对外操作面：

| 族 | 方法 |
| --- | --- |
| 执行 | `exec(*command, timeout, shell=True, user)` → `ExecResult`；内部 `_prepare_exec_command` → `_exec_internal` |
| PTY | `pty_exec_start`、`pty_write_stdin`、`pty_terminate_all` |
| 文件 | `ls`、`rm`、`mkdir`、`read`、`write`、`normalize_path`、`_validate_path_access` |
| 归档 | `persist_workspace()` → `io.IOBase`、`hydrate_workspace(data)` |
| 端口 | `resolve_exposed_port(port)` → `ExposedPortEndpoint` |
| Manifest | `apply_manifest(only_ephemeral=False)` → `MaterializationResult` |
| 状态 | `running()`、`state` property |
| 依赖 | `dependencies()`、`set_dependencies()`、`register_pre_stop_hook()` |

`exec` 的默认 `shell=True` 语义写在 docstring 里：**前缀 `sh -lc`**；传 list 可换前缀。这是 `login` 语义的真正来源。

### 3.3 `SandboxSessionState`（`session/sandbox_session_state.py`）

公共字段八个，同样用 `type` 判别 ＋ `_subclass_registry`：

```
type: str
session_id: uuid.UUID          # 默认 uuid4
snapshot: SerializeAsAny[SnapshotBase]
manifest: Manifest
exposed_ports: tuple[int, ...] # 默认空
snapshot_fingerprint: str | None
snapshot_fingerprint_version: str | None
workspace_root_ready: bool     # 默认 False
```

三个私有属性影响恢复安全：`_path_grants_require_rebind`、`_mount_authority_redacted`、`_mount_authority_rebound`。**恢复时挂载凭据要重新绑定而不是从 state 里读回**——这条直接决定序列化格式，必须移植，不能简化。

### 3.4 `types.py`

| 类型 | 形态 | 要点 |
| --- | --- | --- |
| `User` | `{name: str}` | 按 name 做 hash/eq |
| `Group` | `{name, users: list[User]}` | 按 name 做 hash/eq |
| `Permissions` | `{owner=0o7, group=0, other=0, directory=False}` | `to_mode` / `from_mode` / `from_str`；`from_str` 要处理 `ls` 的 ACL/xattr/SELinux 尾标 `+ @ .`，并认 `s/S/t/T` |
| `FileMode` | IntEnum | `ALL=0o7, NONE=0, READ=4, WRITE=2, EXEC=1` |
| `ExecResult` | `{stdout: bytes, stderr: bytes, exit_code: int}` ＋ `ok()` | **stdout/stderr 是分开的 bytes** |
| `ExposedPortEndpoint` | frozen `{host, port, tls=False, query=""}` ＋ `url_for(scheme)` | 只认 `http`/`ws`；IPv6 加方括号；默认端口省略 |

> `Permissions.owner` 默认 `0o7`（rwx）而 group/other 为 0——**默认是 0700 语义**，与 Rusty `RunTempDir` 的 `0o700` 巧合一致，但那是两回事，不能互相引证。

### 3.6 当前 Rust 增量的验收边界（2026-09-16）

截至首个增量，`ra-core::sandbox` 交付值类型、错误码与错误载荷，**不代表 R8-P1 全部完成**。Client/Session/State、具体 options/state 注册、依赖容器、生命周期装饰层和恢复授权重绑定仍待移植，不能用本增量的测试替代这些验收。后续注册机制增量见 §3.7。

本次审核修复：

- `Permissions` 反序列化省略字段时复用 `Default`（0700、非目录）；`ExposedPortEndpoint` 的 TLS/query 同样保留上游缺省值。
- `owner_can/group_can/others_can` 接受 `FileMode` 或 `u32` 掩码；位或组合返回 `u32`，支持读写、读执行等组合。Rust 的数值掩码使用 `0o6_u32` 等显式类型；builder 消费并返回值，适配 Rust 所有权，不模拟 Python 可变对象别名。
- Python 异常继承用 `ErrorCode` + `SandboxErrorDetails` 表达；`exec_nonzero/exec_timeout/exec_transport/pty_session_not_found` 保留类型化载荷，原始输出字节与供人阅读的有损 UTF-8 context 分开保存。context 覆盖不修改类型化载荷。
- 端口及常用 workspace 错误提供具名构造入口。通用 `SandboxError::new` 仍是低层入口；其余上游异常的具名构造与调用点迁移未宣称全部完成。
- Rust builder 的重试属性在读取时回退到直接 sandbox cause，因而通过 `with_cause` 或 `with_sandbox_cause` 设置原因一致，显式 `Some(bool)` 优先；`None` 表示继承原因或保持未知。此做法适配 Rust 分步构造，避免 setter 调用顺序改变最终语义。

验证：`cargo test --manifest-path tests/it-core/Cargo.toml --test sandbox_contract`，35 项通过；`cargo clippy -p ra-core -- -D warnings` 通过。

### 3.7 注册机制与 Snapshot 值对象增量（2026-09-17）

新增的是显式 `TypeRegistry`、原始 `DiscriminatedPayload` 与最小 `Snapshot` 值对象。`client_options_kind/session_state_kind/snapshot_kind` 仅区分注册表家族和错误策略；不是具体 options/state 的实现，也没有实现挂载授权清理或重绑定。`BaseSandboxClient`、`BaseSandboxSession`、`Manifest`、`SandboxSessionState` 及 state 往返仍未交付；Snapshot 的 IO 行为归 P7（已随 §3.11 交付 local／noop）。

审核修复与 Rust 表达差异：

- 扩展字段不能覆盖 `type`；与 Snapshot 的 `id` 一样，写入保留键的 builder 调用不修改值。序列化最后写入权威 discriminator，normalizer 也不能改成另一种类型。
- state 家族的未知类型和校验失败错误不保留原始 discriminator、验证器 reason 或 source；`Display` 和 `Debug` 都不携带这些敏感数据。非脱敏家族仍保留诊断详情。
- `DiscriminatedPayload` 明确是可构造、可反序列化的未校验数据。`readmit` 重新执行注册验证器，不能照搬上游“已构造的具体模型直接返回”的捷径，因为该原始载荷没有同等的构造校验保证。
- `Snapshot` 保留 `Serialize`，移除无需注册表的 `Deserialize` / `TryFrom<Value>`，`from_payload` 改为私有。持久化恢复先读为 JSON，再调用 `Snapshot::parse(&registry, &value)`，确保未知类型拒绝和具体类型 normalizer 都生效。`new/with_field` 用于受信任的后端配置构造，不是持久化恢复入口。这是显式注册表不能通过普通 serde `Deserialize` 隐式传入所需的适配，没有引入全局注册表。

回归覆盖：保留键覆盖、state 错误的 Display/Debug/source 脱敏、构造／反序列化／修改后 readmit 的验证、接收方 normalizer、Snapshot 经注册表恢复与往返、normalizer 改换类型的拒绝；另有编译失败文档测试防止恢复无注册表的 Snapshot 反序列化入口。

**线格式已用上游实测逐项核对**（`Manifest.model_dump(mode="json")` 与 `describe()`）：条目平铺字段与默认权限 0755（目录型 `directory=true`）、`git_repo` 的 `host/ref/repo/subpath`、`local_dir` 的 `src: null`、`file.content` 为 UTF-8 字符串且非 UTF-8 上游同样报错；挂载的 `mount_path/read_only/mount_strategy`、`pattern.options` 嵌套、`docker_volume.driver_options`；环境的 `{"value": {...}}` 包一层与 `EnvEntry` 的三字段；`describe(depth=1/2/None)` 的树形输出逐行相同。

Rust 表达差异（每条都注明必要性）：

- **`WorkspacePathPolicy` 只移植 POSIX（远端）那一半。** 上游同一个类里还有一条跟随宿主符号链接的路径（`resolve_symlinks`、`root_is_existing_host_path`、`sandbox_path_grant_host_path` 的 `resolve()`），那需要读真实文件系统；`ra-core` 不做 IO 是 §8 的分层裁决。**词法检查不能替代它**：工作区内的符号链接可以指向工作区外，只有解析型检查能发现。该半边随 P3 的 unix-local 落地。
- **`PosixPath` 在构造时按 `PurePosixPath` 的规则整理拼写**：合并重复分隔符、丢掉单独的 `.`、去掉尾部分隔符，保留恰好两个前导斜杠，**但不动 `..`**。不整理会让 `resolve_workspace_path("/w", "./README.md")` 产出 `/w/./README.md`、`anchor("./plot.png")` 产出 `tasks/a/./plot.png`，与上游不一致。解析 `..` 是 `normalized()`，仍与构造分开。
- **`Manifest` 去掉 `Deserialize`，改用 `Manifest::parse(&registry, &value)`。** 条目类型是开放家族，普通 serde 反序列化传不进注册表。与 §3.7 的 `Snapshot` 同一处理。`Environment::parse` 另收一张 env value 注册表，两张表分开是因为家族本来就是两个。
- **`Dir.children` 与 `Manifest.entries` 用 `BTreeMap`（按名排序），不是插入序。** `iter_entries` 仍是前序。上游的插入序不被任何语义依赖（`describe` 自己排序、`ephemeral_entry_paths` 是集合、物化是并发的）。
- **`MountPattern` 是闭合枚举，`MountStrategy` 与 `MountProvider` 开放。** 上游 `pattern` 字段就是四选一的判别联合（未注册的工具直接拒），而 `MountStrategyBase` 和 `BaseEntry` 有子类注册表。三者的开闭跟着上游走。
- **挂载权限位不生效，Rust 直接固定而不告警。** 上游 `warnings.warn` 后覆盖；没有任何值会被兑现，日志只是把一次无效配置写进流水。文档写明访问控制在 provider 侧配置。
- **`Environment::resolve` 的兄弟取消由 combinator 提供。** 上游需要专门的 `gather_with_cancel`，因为 `asyncio.gather` 出错即返回、剩余任务仍在跑；Rust 里 `try_join_all` 出错即被丢弃，丢弃 future 就是取消。语义相同，不另写并发原语。
- **`GitRepo` 的 `ref` 字段在 Rust 叫 `reference`**（`ref` 是关键字），线上仍写 `ref`。
- **`EntryContent::Mount` 装箱**：挂载带着整套 provider 凭据字段，不装箱会让每个条目都按最大的挂载算大小。
- **截断的定点搜索加了 8 轮上限。** 标记文本里写着被丢掉多少字符，它自己的长度又取决于那个数字；上游的循环没有出口，相差一位数字的两个长度可以互相换位。到上限就采用最后一次测量。
- **不做截断日志。** 上游 `logger.warning`；截断本身已经写在输出里（而且是给模型看的那句），比日志更有用，`ra-core` 也不引入日志副作用。
- `PathGrantError` 新增 `NotAGrant`／`PathMissing`／`FieldType`：上游由 pydantic 的必填与类型校验报出，Rust 手写读取需要自己命名这三种；其余六条错误文案与上游逐字相同。
- **渲染省略空集合**（entries／environment／users／groups／extra_path_grants）。上游一律写出空集合。两边所有字段都有默认值，互相都读得进；差别只在空 manifest 写多少字节。此为前一批已有的取舍，本批沿用未改。

**本批未移植、明确留给后续的**：

- 挂载生命周期本身——`MountPattern.apply/unapply`、rclone 配置合成、`teardown_for_snapshot`／`restore_after_snapshot`、`InContainerMountAdapter`／`DockerVolumeMountAdapter`、`build_docker_volume_driver_config` 的选项拼装。都要一个活的 session 去执行命令，归 P3/P7/P8 与服务 crate。
- `validate_mount_activation_credential_boundary`：激活时的凭据边界检查，需要活 session、`provider_backend_id` 和解析后的挂载路径。本批交付的分类表与 `acknowledges_*` 查询是它的输入。
- `_mount_security.py` 的错误脱敏装饰器（`redact_mount_error_data` 等）：包的是 async 生命周期调用，同上。
- `_mount_security.py` 的「可信类来源」判定（`_mount_entry_class_is_trusted` 等）：靠 Python 的 `__module__`/`__qualname__` 比对防止导入顺序伪装，Rust 没有等价问题——内建注册表里的类型就是内建的。
- `gather_in_order` 与 `SandboxConcurrencyLimits`：物化的并发限流，归执行方与 P4 的 run config。
- `_coerce_manifest` 的「以映射形式提供的 manifest 不得声明 `extra_path_grants`」：run config 强制点，随 P4。
- 会话侧的 manifest application／mount lifecycle 顺序（`_apply_entry_batch` 等）：需要服务 crate。

Rust 表达差异（每条注明必要性）：

- **`supports_pty()` 返回 `false`，上游是 `true`。** PTY 实现归 P5；在它落地前宣称有终端，会让工具面装上一个调用即失败的交互写入工具。这是**本批明确的缺口**，不是裁决。
- **state 用扩展字段而不是子类。** 上游每个后端一个 `SandboxSessionState` 子类；Rust 侧 state 是单一类型 ＋ 随行的后端字段（§3.3／§3.7 的形状）。`workspace_root_owned` 因此是 `state.field("workspace_root_owned")`，附带的好处是不认识本后端的宿主往返它时也不会丢。
- **客户端构造拆成三个函数。** 上游 `__init__` 有两种运行期错误：给了 allowlist 却没关继承、allowlist 传了字符串。前者在 Rust 里「指定 allowlist」本身就意味着关继承，后者参数是 `IntoIterator<Item = String>`，`&str` 不满足。两条错误因此**不可表达**而不是不移植；对应的上游测试没有 Rust 对照物。
- **`Environment::resolve` 要宿主 resolver。** 这是 §3.8 的既有形状（上游是每个 `EnvValue` 子类自己 `resolve()`）。客户端持一个 `Arc<dyn EnvValueResolver>`，默认 `UnresolvableEnvValues`，可用 `with_env_value_resolver` 换。
- **`read(user=…)` 的「不存在 vs 不可读」判定简化。** 上游用一段自己解析符号链接的 `READ_PATH_PROBE_V3` 脚本；这里改问 `[ -e "$1" ]`。差别只在一种情况：父目录对该账号不可搜索时，上游报 not-found 的分支这里报读取失败。完整探针随 runtime helper 脚本一起补。
- **宿主路径解析改为可失败的 `Result<PathBuf, SandboxError>`。** Python 可通过异常报告循环；Rust 必须显式把错误传到调用者，不能把未解析完的路径当作授权结果。`HostWorkspacePaths::new` 与 `sandbox_path_grant_host_path` 同步返回 `SandboxError`，根、grant、普通路径、exec 围栏和归档恢复均传播解析失败。合法长链完整解析，不设置固定层数上限；缺失路径仍保留，支持新文件写入。循环与无法完成授权解析的 IO 错误返回 `SandboxConfigInvalid`（exec／归档入口再包装为各自错误）。这是服务层的错误表达；部分 Python 版本的 non-strict resolve 会保留循环或不可访问分量，本实现明确拒绝此类未完成解析，避免把残余符号链接交给后续 IO 继续跟随。
- **路径策略不缓存。** 上游按 `(root, grants)` 缓存 `WorkspacePathPolicy`；这里每次重建，因为 manifest 在锁后面、生命周期会写它，缓存键一旦过期就是在回答上一份 manifest 的问题。
- **归档成员名没有 `./` 前缀。** 上游 `tar.add(root, arcname=".")` 产出 `./src/main.rs`，`tar` crate 写入时会去掉这个前缀，成员名是裸相对路径。互读没问题（上游 `_tar_member_rel_variants` 两种都认，本侧解析时丢掉 `.` 分量），但**同一个工作区两边产出的字节不同**，跨实现比指纹时要知道这一点。
- **删除工作区时，manifest 声明了挂载就整个不删。** 上游先 `unmount` 每个 ephemeral 挂载、有一个失败就不删根。挂载生命周期未移植，所以「声明了挂载」直接走「卸载失败」那条分支——这是保守侧，不会删掉挂载另一头的东西。
- **`create` 不提前拒绝声明了账号的 manifest。** 上游只在物化与 `provision_manifest_accounts` 里拒；提前到 `create` 会让本 client 拒掉上游允许持有的配置（同一份 manifest 可以交给容器后端）。
- **`apply_manifest` 遇到带条目的 manifest 直接报错。** 物化未移植（见下），返回空回执会让一个声明了文件的工作区静默地空着启动。

| `extract()` 解压到工作区子路径、`apply_patch` | P6/P7 |

**指定 `user` 的文件操作只测到命令成形那一层。** 上游用一个覆写 `_exec_internal` 的录制子类断言 `sudo -u … -- sh -lc …` 的形状；Rust 侧没有这个继承缝，`sudo` 又需要机器上真有第二个账号且免密，所以改为把 `prepare_exec_command` 公开出来直接断言成形（`unix_local_command_shape`），端到端那一段——以该账号检查、再本地执行——**没有实测记录**。为此公开一个函数是刻意的：它同时是宿主做日志与审批时想要的那个答案。

另有一处**本地与远端语义不同、两边都照上游**，值得单独记：本地 `normalize_path` 连叶子一起解析，所以 `rm` 一个符号链接删的是目标、留下悬空链接；上游远端 `_validate_remote_path_access` 只拿解析结果做越界判定、操作仍落在链接上。这不是偏差，是上游两条路径本来就不同，测试里各自断言。

### 3.10 R8-P3 第二批：manifest 物化（2026-09-22）

落地 `ra-sandbox::materialize{,::gather,::local,::git,::errors}`，对应上游 `session/manifest_application.py::ManifestApplier`、`session/manifest_ops.py`、`materialization.py::gather_in_order`、`entries/artifacts.py` 五个 `apply()` 与 `entries/base.py::_apply_metadata`。P2 交付的声明面到此有了执行方：`UnixLocalSandboxSession::apply_manifest` 不再对带条目的 manifest 报错。

交付与上游对应：

| Rust | 上游符号 | 说明 |
| --- | --- | --- |
| `ManifestApplier::{apply_manifest, apply_ephemeral}` | `ManifestApplier.apply_manifest(only_ephemeral=…)` | 建根 → 造账号 → 解析每条目标路径 → 交批执行 |
| `ManifestApplier::provision_accounts` | 同名 | `groupadd` → 去重后的 `useradd -U -M -s /usr/sbin/nologin` → `usermod -aG`，顺序照移 |

| `UnixLocalSandbox{Client,Session}::with_concurrency_limits` | `BaseSandboxSession._apply_concurrency_limits` | 见下 |

Rust 表达差异（每条注明必要性）：

- **`apply()` 不挂在 `Entry` 上，改由 `ra-sandbox` 按 `EntryContent` 分派。** §3.8 已裁决 `ra-core` 只放声明、不做 IO；把 `apply()` 挂回条目会让 `ra-core` 直接依赖文件系统与 `SandboxSession`。代价是**宿主注册的条目类型（`EntryContent::Extension`）没有物化实现**——manifest 解析得进来，物化时明确拒绝而不是静默跳过。这是本批的已知缺口，不是裁决。
- **`only_ephemeral` 拆成两个方法。** 上游一个方法两个旗标，而公开入口永远传 `provision_accounts=not only_ephemeral`；四种组合里只有两种存在，拆开后写不出第三种。
- **`_prune_to_ephemeral` 没有对应物。** 上游只在 `artifact.ephemeral` 为真时调它，而它开头两个分支就把这种输入全接走了，剪枝体不可达。Rust 侧实现的是可达行为：**ephemeral 目录整棵重建，包含其中非 ephemeral 的子项**（上游 `test_manifest_applier_only_ephemeral_reapplies_full_ephemeral_directories` 断言的就是这个），已选中路径的后代跳过。
- **`gather_in_order` 使用带序号的 `buffer_unordered`。** 按完成顺序观察首错并取消同批 future，成功结果按输入序号恢复顺序；已完成的条目立即释放并发名额，不被前面的慢条目阻塞。对应上游 `FIRST_EXCEPTION` 与 worker 持续领取下一项的行为。
- **Git 清理由独立 Tokio task 持有会话并执行。** `ManifestApplier::new` 接收 `Arc<dyn SandboxSession>`；本地 session 的内部句柄共享 state 和 running 标志。Rust 的 future drop 无法执行异步 `finally`，因此检出 task 在调用方取消时停止当前操作、再执行 `rm`；批次错误返回前等待所有检出清理。调用方直接丢弃整个 application future 时，清理继续运行于当前 Tokio runtime，调用方无法同步等待它；runtime 必须保持运行。正常错误仍沿用上游的清理顺序和错误优先级。这是 Rust 异步所有权的必要适配，不把额外策略塞进 provider-neutral core。
- **本地 exec 在取消时终止整个进程组。** 参考 codex 的进程组回收机制，以 drop guard 在 Git 清理启动前发送 SIGKILL，并让 Tokio 回收直接子进程；避免取消后 clone/cp 继续写入。这里使用立即终止，未引入 codex 产品层的 TERM 宽限期配置。
- **只移植钉住目录句柄的那条遍历路径。** 上游另有不带 `dir_fd` 的回退实现给没有 `openat` 的平台；本批 `materialize` 模块和 unix-local 后端都受 `cfg(unix)` 保护，crate 的其余声明与工具仍可在非 Unix 平台编译。
- **目录条目里按名排序。** `list_files` 对结果排序：上游按文件系统返回顺序拷贝，回执顺序因此随目录实现变化；回执是给人对账的，同一棵源目录两次跑应当得到同一份。
- **拷贝走内存而不是流。** `SandboxSession::write` 收 `Vec<u8>`（既有形状），所以一个文件是读满、算 sha256、再写；上游 `seek(0)` 复用同一个句柄。单文件大小因此受内存约束，这一条随 write 的流式化一起改。

- **取消清理是本移植独有的一层，上游不需要。** 上游 `GitRepo.apply` 把 `rm -rf` 放在 `finally` 里，asyncio 取消一个协程时那段照样跑完；**Rust 丢弃一个 future 不会 await 任何东西**，而 `gather_in_order` 首错即丢弃兄弟任务，所以照抄「`finally` 里删」会让一次失败的批次留下 `/tmp/sandbox-git-…` 和一个仍在写的子进程。三处改动合起来补这个洞：①`ManifestApplier` 持 `Arc<dyn SandboxSession>` 而不是借用，检出才能搬进一个能活过调用方的 `tokio::spawn`；②该 worker 用 `select!` 监听一个 drop 信号，无论完成还是被取消都执行同一句删除，句柄进 `CleanupTasks`，`apply_entries` 在返回前 `wait()`——物化报完成时清理一定已经结束；③`unix_local::exec::run` 加 `kill_on_drop(true)` 与 `ProcessGroupGuard`，被丢弃的 exec 在清理开始前先杀掉整个进程组，这正是 worker 那句删除能成立的前提（否则删完还会被重新创建）。验收在 `manifest_application::{dropping_an_application_cancels_checkout_and_finishes_cleanup, a_batch_failure_waits_for_cancelled_checkout_cleanup, a_later_failure_cancels_an_earlier_pending_entry}` 与 `unix_local_exec::dropping_exec_stops_descendants_before_they_can_write_again`。
- **拷贝目录途中的 IO 失败报 `local_dir_read_error` / `local_checksum_error`，上游报 `local_file_read_error`。** 上游这个分叉来自 `except OSError` 捕不到自家的 `LocalDirReadError`，是异常层级的副产物。**调用方真正分支用的那四种拒绝——`symlink_not_supported`、`path_changed_during_copy`、`outside_base_dir`、`path_not_found`——两边错误码与 `reason` 完全一致**，`local_file` 那条路径的重包装（丢掉 `src`、保留其余 context）也逐字照移。
- **限额由 client/session 在构造时接收。** 上游从 run config 取、在 session 建好之后调 `_apply_concurrency_limits`；run config 归 P4 未移植，所以暂时挂在 client 上（与环境策略同理：这是跑 SDK 的进程对自己机器的决定）。P4 接线时换成传一个 `SandboxConcurrencyLimits`，不再新增两个数字。
- **`SandboxConcurrencyLimits` 放在 `ra-core::sandbox::materialization` 而不是 run config 模块。** 它是它约束的那个结果类型的邻居，而 run config 这个模块还不存在；零值用 `ConcurrencyLimitError` 拒绝，对应上游 `__post_init__` 的 `ValueError`。

**本批未移植、明确留给后续的**：

| 缺口 | 归属 |
| --- | --- |
| 挂载条目的物化（`Mount.apply`、`MountPattern.apply/unapply`、rclone 配置合成） | P7/P8；当前**明确拒绝**，不返回空回执 |
| 宿主注册条目类型（`EntryContent::Extension`）的物化 | 需要宿主侧可执行的扩展点，未设计；当前明确拒绝 |
| `apply_manifest` 前的 `_validate_manifest_application`（挂载凭据边界）与 `redact_mount_error_data` | P7/P8，与 §3.9 同一条 |
| `LocalDir.apply(user=…)`：以另一账号建目录与写文件 | 本后端拒绝账号，调用点也从不传 user；随容器后端 |
| 流式拷贝（`session.write` 收句柄而不是字节） | 随 `SandboxSession::write` 的形状变更 |

**两条本后端上的事实，值得单独记，因为它们会让人以为移植漏了东西**：

1. **`reapply_ephemeral_manifest` 在 unix-local 上走不到。** 协议默认只在「工作区内容跨停机保留」时调它，而本后端 `workspace_state_preserved_on_start()` 取默认 `false`、`snapshot_restorable()` 也是 `false`，所以每次 start 都是全量物化。实现它是因为它是快照生命周期（P7）要接的那个入口；测试直接调 `ManifestApplier::apply_ephemeral` 验证。
2. **macOS 上 `git_repo` 条目跑不通，这是上游同款行为不是本移植的缺陷。** 检出按上游写进 `/tmp/sandbox-git-…`，而 macOS 的 `sandbox-exec` profile 里 `/tmp` 与 `/private/tmp` 都在那 12 条 deny 里（§3.9 已记，逐条照抄上游 `unix_local.py`）。上游同一份 profile、同一个 `/tmp` 路径，结论一样。命令序列因此用录制 session 验证，没有真实 `git clone` 的实测记录。

另有一条**上游行为容易被当成 bug**：`local_file` 的源文件不存在时，`reason` 是 `path_changed_during_copy` 而不是 `path_not_found`。因为单文件是按「父目录的唯一子项」拷的，父目录在、只有叶子缺，`path_not_found` 只留给源**根**。两边一致，测试里写明了为什么。

### 3.11 R8-P7 第一批：snapshot 三族、规格与本地存储（2026-09-22）

落地 `ra-core::sandbox::snapshot` 的三种快照、规格与解析，以及 `ra-sandbox::snapshot{,::defaults}` 的存储实现，对应上游 `sandbox/snapshot.py` 与 `sandbox/snapshot_defaults.py` 两个文件。§3.7 只交付了共享基座（判别载荷 ＋ 最小 `Snapshot` 值对象），当时明确写「Snapshot 的 IO 行为仍归 P7」——这一批把 IO 补上，**但只到存储这一层**：session 生命周期的接线（持久化、恢复、指纹）是 P7 下一批。

交付与上游对应：

| Rust | 上游符号 | 说明 |
| --- | --- | --- |
| `snapshot::{NOOP,LOCAL,REMOTE}_SNAPSHOT_TYPE` | `NoopSnapshot/LocalSnapshot/RemoteSnapshot.type` | 三个判别符 |
| `Snapshot::{local,remote}`、`local_base_path`、`remote_client_dependency_key` | 两个子类各自的字段 | 字段进 §3.7 的判别载荷；读取器按类型把关，`remote` 上的 `base_path` 读不出来。`local` 可失败，见下方 `SnapshotPathError` 那条 |
| `builtin_snapshot_registry` | `SnapshotBase._subclass_registry` ＋ 模型必填字段 | 解析持久化载荷时，`local` 缺 `base_path`、`remote` 缺 `client_dependency_key` 一律拒绝 |
| `SnapshotSpec`（三变体）＋ `build` | `LocalSnapshotSpec`/`NoopSnapshotSpec`/`RemoteSnapshotSpec` ＋ `SnapshotSpecUnion` | 闭合判别联合，serde `tag = "type"`，线格式逐条对过 |
| `SnapshotSource` ＋ `resolve_snapshot` | `resolve_snapshot(spec: SnapshotBase \| SnapshotSpec \| None, snapshot_id)` | 给定快照原样返回（**id 不改写**），规格按 session id 构造，`None` 走 noop |
| `CreateRequest::{snapshot, with_snapshot_spec}` ＋ `UnixLocalSandboxClient::create` | `UnixLocalSandboxClient.create(snapshot=…)` 里的 `resolve_snapshot(snapshot, str(session_id))` | 之前只能传已命名的快照，规格这条路补上 |
| `ra-sandbox::snapshot::{SnapshotStore, BuiltinSnapshotStore}` | `SnapshotBase.persist/restore/restorable` | 见下方第一条差异 |
| local 的三件 | `LocalSnapshot.persist/restore/restorable` ＋ `_path`/`_filename` | `<id>.tar`、临时文件＋rename、失败清临时文件、`is_file()` 判定 |
| noop 的三件 | `NoopSnapshot` 同名三件 | persist 无操作；restore 报 `SnapshotNotRestorable`，path 为 `<noop>`；restorable 为 `false` |
| `SandboxError::{snapshot_persist,snapshot_restore,snapshot_not_restorable}` | `SnapshotPersistError`/`SnapshotRestoreError`/`SnapshotNotRestorableError` | 消息、`op`、`snapshot_id`／`path` context 与 retryable 逐项一致 |
| `snapshot::defaults::{HostPlatform,SnapshotHost,default_local_snapshot_base_dir,cleanup_stale_default_local_snapshots,resolve_default_local_snapshot_spec,DEFAULT_LOCAL_SNAPSHOT_TTL}` | `snapshot_defaults.py` 的四个函数与两个常量 | 三平台分支、`XDG_STATE_HOME`／`%LOCALAPPDATA%`／`%APPDATA%` 的绝对性判定、30 天 TTL、只删 `*.tar`、目录 `0o700` |

Rust 表达差异（每条注明必要性）：

- **三件 IO 挂在 `SnapshotStore` 上，不挂在快照对象上。** 上游靠子类给快照加存储，而这里的快照是要随 state 序列化的数据——从磁盘读回来的载荷本来就得重新找实现。所以宿主的扩展点从「继承 `SnapshotBase`」换成「实现 `SnapshotStore`」。代价是 `BuiltinSnapshotStore` 认不得的类型一律拒绝而不是静默当空，和 §3.10 的 `EntryContent::Extension` 同一处理。
- **收发整段字节，不收发流。** `SandboxSession::{persist_workspace,hydrate_workspace}` 已经是 `Vec<u8>`（§3.9 的既有形状），上游用 `shutil.copyfileobj` 分块拷。因此上游「拷到一半 `read()` 抛错」那条原子性用例在 Rust 里不可表达，改用「目录不可写」触发同一条清理路径：旧快照原样、临时文件不留。两者验的是同一个保证。
- **`base_path` 不是 UTF-8 就拒绝，`Snapshot::local`／`SnapshotSpec::build`／`resolve_snapshot` 因此可失败（`SnapshotPathError`）。** 上游的 `Path` 随对象一起活在进程里，不需要编码；这里它要进 JSON 载荷、随 state 落盘。**最初写的是 `to_string_lossy()`，那是个会丢数据的 bug**：非法字节一律变成同一个 U+FFFD，于是两个只在这些字节上不同的目录会映射到同一个存储位置——审核实测复现了「先后用同一个 id 存两次、恢复第一个拿到第二个内容」。改成显式拒绝：`SnapshotSpec::Local` 的字段是公开的，所以 `build` 是最后一道能挡住它的地方。`ra-sandbox::snapshot::defaults::resolve_default_local_snapshot_spec` 同理——默认目录由账号 home 拼出来，非 UTF-8 的 home 在建目录之前就报 `SandboxConfigInvalid`，不把一个用不了的 spec 交出去。回归用例 `sandbox_snapshot::two_directories_that_differ_only_in_unreadable_bytes_cannot_name_the_same_storage` 钉住两条路径的 lossy 渲染确实相同、而三个入口都拒绝。
- **id 单段校验写成显式规则，不借 `PurePosixPath`/`PureWindowsPath`。** 规则是实测对齐上游两种拼写后得到的：空、`.`、`..`、含 `/` 或 `\`、开头 `<ASCII 字母>:` 一律拒。**`:a`、`ab:c` 这类上游接受的名字这里同样接受**——盘符要求冒号前恰好一个字母，把它们一起拒掉会比上游更严，有回归用例钉住。
- **`ValueError` 变成 `SandboxConfigInvalid`。** Rust 没有那条异常通道；错误码取配置类，消息保留 `single path segment` 这半句，三个操作（persist/restore/restorable）都在用路径之前拒绝，与上游 `_path()` 的位置一致。
- **`HostPlatform` 三分支代替 `sys.platform` ＋ `os.name` 两个字符串。** 上游四个 keyword-only 参数里只有三种组合描述真实宿主；`SnapshotHost` 把 home／env／platform 一起显式传入，Windows 分支因此在 macOS 上也有实测，而不是只在 Windows 上才跑到。
- **默认目录是 `rusty-agent/sandbox/snapshots`，上游是 `openai-agents-python/sandbox/snapshots`。** 这是用户账号下本产品自己的 state 目录，不是互读格式；照抄上游的发行包名会让两套 SDK 的归档混在一处。
- **UNC 判定在本模块自己实现。** `ra-core` 的 `windows_absolute_path`（§3.8 的既有形状）只认盘符，因为它的调用点先拒反斜杠；而 `%LOCALAPPDATA%` 允许 `\\server\share`，上游 `PureWindowsPath.is_absolute()` 认它。实测确认的规则是「恰两个分隔符 ＋ 非空 server ＋ 非空 share」，`\\server`、`\\server\\share`、`///server/share` 都不算。没有改 `ra-core` 那个函数：它的语义由 P2 的调用点定义，改它会波及 cwd 与授权判定。
- **`max_age_seconds < 0` 的早退不可表达。** `Duration` 非负；`now.checked_sub(max_age)` 溢出时仍然早退，对应上游「时间算不出来就什么都不删」的那一半。
- **建目录失败报 `SnapshotPersistError`。** 上游直接把 `OSError` 抛给调用方；Rust 侧要一个 sandbox 错误码，取了它所属的那一族，消息写明是默认目录。

**本批未移植、明确留给后续的**：

| 缺口 | 归属 |
| --- | --- |
| `RemoteSnapshot` 的 persist/restore/restorable（`_require_client_method` 的鸭子类型检查与 `<remote:key>` 路径） | 需要 `Dependencies` 注入（P1）；声明面已在，三个操作当前**明确拒绝** |
| snapshot 生命周期接线：`session/snapshot_lifecycle.py` 全部、`tar_workspace.py`、`workspace_payloads.py`、`_clear_workspace_root_on_resume`、指纹计算与缓存、`archive_extraction.py` | P7 下一批；`snapshot_restorable()` 因此仍取协议默认 `false`，unix-local 尚未接 store |
| `SandboxArchiveLimits`（归档成员数与字节上限） | P4/P7，与 §3.9 同一条 |
| 宿主自有快照类型的存储实现 | 扩展点（`SnapshotStore`）已在，注入点随 P4 接线 |

**上游一处容易被当成 bug 的行为，这里照移**：`resolve_snapshot` 收到一个已命名的快照时**不改它的 id**，即使调用方同时传了 session id。理由在上游注释之外：调用方点名的是某一份已存储的工作区，改名会让这次 session 持久化到没人要求的位置，恢复时又去一个什么都没有的地方读。测试里写明了这一点。

验证：`cargo test --manifest-path tests/Cargo.toml -p it-sandbox`，168 项通过（既有 127 项 ＋ 新增 `snapshot` 22、`snapshot_defaults` 18，以及 `unix_local_client` 的规格解析用例 1 条）；`cargo test --manifest-path tests/Cargo.toml -p it-core --test sandbox_*` 十一个二进制 240 项通过（新增 `sandbox_snapshot` 11）。`cargo clippy -p ra-core -p ra-sandbox --all-targets -- -D warnings`、两个 workspace 的 `cargo check --all-targets`、`cargo fmt --check`、`cargo test -p ra-core -p ra-sandbox --doc`、`cargo xtask layering`、`cargo xtask no-inline-tests` 通过；`cargo check -p ra-sandbox --target x86_64-pc-windows-gnu` 通过（既有 `DEFAULT_WORKSPACE_PREFIX` dead-code warning）。`cargo xtask public-api` 的扩展安全计数 ①＝3、②＝52，与 §3.10 记录一致（**本批零新增**：三个新枚举 `SnapshotSpec`／`SnapshotSource`／`HostPlatform` 都加了 `#[non_exhaustive]`）；对账增量 738 → 759，新增的 21 条全部是 snapshot 相关公开项，与既有情况一样源于 `api/` 基线早于整个 sandbox 模块，是否 bless 仍由基线维护单独决定。

审核修复（2026-09-22）：`Snapshot::local` 原先用 `to_string_lossy()` 把目录写进载荷，两个只在非法 UTF-8 字节上不同的目录会折叠成同一个存储位置（实测可让一个 session 恢复出另一个的工作区）。改为显式拒绝并把错误传播到 `SnapshotSpec::build`、`resolve_snapshot` 与 unix-local 的 `create`；`resolve_default_local_snapshot_spec` 在建目录前先拒非 UTF-8 的默认目录。新增 2 项回归用例（`it-core` 的路径碰撞、`it-sandbox` 的非 UTF-8 home），其余用例随构造器改为可失败同步更新。

## 4. 运行集成

### 4.1 `SandboxRunConfig`（`run_config.py`）—— 九个字段

| 字段 | 默认 | 语义 |
| --- | --- | --- |
| `client` | None | 建/恢复 session 的客户端 |
| `options` | None | 建新 session 时的客户端特定选项 |
| `session` | None | **外部 live session 覆盖**（本进程内） |
| `session_state` | None | 不用 `RunState` 时的显式恢复来源 |
| `manifest` | None | 建新 session 的 manifest 覆盖 |
| `snapshot` | None | 建新 session 用的快照 |
| `concurrency_limits` | `SandboxConcurrencyLimits()` | 物化并发 |
| `archive_limits` | **None** | None＝不施加 SDK 归档限制；要默认值须显式传 `SandboxArchiveLimits()` |
| `cwd` | None | **模型可见的工作目录**，相对 workspace root |

`cwd` 的语义边界写得很死，必须原样移植：它**只改相对路径解析**，不限制 run、不阻止访问会话策略允许的其他路径、不改 `Manifest.root`、不改 `BaseSandboxSession` 的直接路径行为。内建的 `exec_command` / `view_image` / `apply_patch` 从它解析相对路径；自定义能力必须自己应用绑定的 `SandboxWorkspaceScope`。校验时目录必须存在且对配置用户可访问；新建 session 时 runner **先物化 manifest 再校验 cwd**。

两个限额类型：
- `SandboxConcurrencyLimits{manifest_entries, local_dir_files}`
- `SandboxArchiveLimits{max_input_bytes, max_extracted_bytes, max_members}`，`__post_init__` 即校验，全都 `>= 1` 或 None。

### 4.2 `SandboxAgent`（`sandbox_agent.py`）

继承 `Agent[TContext]`，加四个字段：

```
default_manifest: Manifest | None = None
base_instructions: ...                       # 沙箱基座指令
capabilities: Sequence[Capability] = Capabilities.default()   # [Filesystem, Shell, Compaction]
run_as: User | str | None = None
```

### 4.3 runtime 三件套

| 模块 | 职责 |
| --- | --- |
| `runtime.py::SandboxRuntime` | 面向 Runner 的门面：`enabled`、`current_session`、`prepare_agent`、`cleanup`、`apply_result_metadata`、`assert_agent_supported`，以及 memory 入队两个口子 |
| `runtime_agent_preparation.py` | 纯函数层：`clone_capabilities`、`prepare_sandbox_agent`、`prepare_sandbox_input`、`build_sandbox_instructions`、`resolve_instructions`、`resolve_sandbox_model_name`、`get_default_sandbox_instructions` |
| `runtime_session_manager.py::SandboxRuntimeSessionManager` | session 的建/恢复/清理与所有权：`acquire_agent`、`ensure_session`、`serialize_resume_state`、`cleanup`、`_create_resources` |

**所有权是这层的核心裁决**，`_SandboxSessionResources` 持 `owns_session: bool`：
- 外部传入的 live session → `owns_session=False`，资源 `cleanup` 直接返回，不停不删；`ensure_started` 才检查 `running()`，已运行则不重复 start，未运行则启动。manifest 的有限更新发生在资源准备阶段，不是 cleanup；
- client 创建或恢复出来的 → `owns_session=True`，由本层负责收尾。

还维护**按 agent 的资源与恢复身份**（`_resume_agent_base_key`、`_resume_state_payload_for_agent`），即一个 run 里多个 agent 各自有自己的 session 与恢复条目。

> 这一条直接否掉旧 R8-10 的「一个 run 一个容器、run 结束一律删」。

**选择优先级**（`_create_resources`）：先取显式 live `session`，此分支不创建／恢复；否则先取 `session_state`，若 `_resume_state_payload_for_agent` 返回当前 agent 对应的 RunState payload，则反序列化并覆盖显式 state，再标记持久化授权；有有效 state 则 resume，否则 create。不能把“整个 RunState 存在”当作“当前 agent 有可恢复条目”。fresh create 才检查 options 必填条件，允许默认 options 的 client 除外；resume 不走 fresh create 的 manifest/options 路径。live session 的 manifest 更新与 resume 的授权重绑定分别处理。

**运行资源清理**：按 agent 逐个尝试清理，即使前一个失败也继续处理其余；仅全部成功后序列化新的 resume state；最后清空运行内资源表并释放 agent guard。结果层对 cleanup 失败如何处理另按普通／流式路径测试，不能把资源 cleanup 抛错直接等同于整次成功结果被改成失败。

## 5. `Capability` 契约（`capabilities/capability.py`）

pydantic 模型，字段 `type`、`session`、`run_as`、`workspace_scope`（后三者 `exclude=True`，不进序列化）。

绑定三步：`bind(session)`、`bind_run_as(user)`、`bind_workspace_scope(scope)`。
克隆：`clone()` 逐字段深拷，但对 session/scope/锁/工具对象**故意不拷**（`_clone_capability_value` 白名单）。

六个可覆盖点：

| 方法 | 默认 | 用途 |
| --- | --- | --- |
| `required_capability_types()` | `set()` | 声明必须共存的能力 |
| `tools()` | `[]` | 贡献模型可见工具 |
| `process_manifest(manifest)` | 原样 | 改 manifest |
| `instructions(manifest)` | None | 追加确定性指令片段 |
| `sampling_params(params)` | `{}` | 追加模型请求参数 |
| `process_context(context)` | 原样 | 采样前改模型输入 |

默认集 `Capabilities.default()` = `[Filesystem(), Shell(), Compaction()]`。
- `Filesystem.tools()` → `[view_image, apply_patch]`
- `Shell.tools()` → `[exec_command]`，**仅当 `session.supports_pty()` 才追加 `write_stdin`**

## 8. Rust 模块与依赖落点（裁决）

保留 `xtask/src/layering.rs::ALLOWED_INTERNAL_DEPS` 的 `ra-runtime → ra-core` 约束。撤回 runtime 直接依赖同时包含后端的 `ra-sandbox` 提案；协议与具体后端分开，不能通过允许一条反向依赖把 exec、tools 和 Docker 间接带进运行内核。

| 落点 | 内部依赖／消费者 | 职责 |
| --- | --- | --- |
| `ra-core::sandbox`（新增模块） | 不增加内部 crate 依赖；由 runtime、工具和后端消费 | 上游中立的 client/session/capability 协议与共享值、错误、manifest/state 表达、snapshot/dependency 接口。runtime 需要的 SandboxAgent 配置使用组合表达；options/state 的后端扩展通过显式注册与类型擦除传递，不能用封闭的内置后端枚举堵住第三方 client。具体 Docker 字段和 IO 实现不放这里。 |
| `ra-sandbox`（拟新增服务 crate） | `ra-core`、`ra-exec`、`ra-tools`；产品装配层消费 | session 共用生命周期实现与装饰层、物化／snapshot／sinks 的具体 IO、Unix-local/Docker client，以及默认 capabilities 的具体实现。默认能力通过 ra-tools 创建绑定 session 的工具；对外提供其共享协议实现。 |
| `ra-tools::sandbox` | 新的 session 工具只依赖 `ra-core::sandbox` 协议；现有 exec/patch 依赖保留 | exec/write_stdin/patch/view_image 的上游工具形态与绑定；不依赖 ra-sandbox，避免 `ra-sandbox → ra-tools → ra-sandbox` 环。 |
| `ra-runtime` | **仍只依赖 ra-core** | RunConfig 的 sandbox 配置引用核心协议；运行资源选择、按 agent 的身份与 owned/borrowed、preparation/cleanup 调用注入的 client/session/capability。不能直接构造具体后端或工具。 |
| 产品／SDK 装配层 | 可依赖 ra-runtime、ra-sandbox；coding 产品继续依赖 ra-tools | 构造并注入客户端及默认 capability 实现、snapshot 工厂、后端注册表；提供构建 SandboxAgent 的便利入口，保持上游默认集与配置语义，不要求模型调用者手工凑三种能力。已有更严格配置单独选择。 |

**实际调用链**：装配层构造具体 client 与 capability 实例 → 经核心协议放进 sandbox agent/run 配置 → runtime 调用 client.create/resume 或使用 borrowed session → capability 绑定同一 session，产出核心 Tool 协议对象 → runtime 通过既有派发调用工具 → 工具调用 session 协议 → 后端执行。runtime 不需要知道实现在哪个 crate。

**Compaction 等跨章能力**：其共享协议先登记在核心，具体能力由服务层装配已有机制；需要其他服务依赖时在对应任务核对现有允许方向并补精确边，不允许反向依赖 runtime。未核对的实现细节仍列 §11，不据此另建 compaction 引擎。

**注册方式确定为宿主显式装配**；装配入口自动登记选用的内置实现，第三方实现可追加。保留上游类型判别、未知类型与重复登记错误，Rust 不照搬 Python 导入时副作用。P1 实现时同步登记新 crate 分层与允许边，必须验证无环和 runtime 仍仅依赖 core。本次仅裁决文档，不修改代码或放宽现有门禁。
