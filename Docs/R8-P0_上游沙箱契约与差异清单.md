## 3. 核心协议

### 3.1 `BaseSandboxClient`（`session/sandbox_client.py`）

泛型 `Generic[ClientOptionsT]`，类属性两个：`backend_id: str`、`supports_default_options: bool = False`。

公共方法五个：

| 方法 | 形态 | 契约要点 |
| --- | --- | --- |
| `create(...)` | async | 建新 session；建前走 `_validate_manifest_for_create` |
| `resume(...)` | async | 从 state 恢复 |
| `delete(session)` | async | 返回 `SandboxSession`，**不是 None** |
| `serialize_session_state(state)` | sync | → `dict[str, object]` |
| `deserialize_session_state(payload)` | sync | ← `dict[str, object]` |

内部三处必须一起移植的行为：`_wrap_session`（instrumentation 包装）、`_resolve_dependencies`、`_serialize/_deserialize_session_state_payload`（子类可覆盖的序列化钩子）。

`BaseSandboxClientOptions` 是 **pydantic 模型 ＋ 子类注册表判别联合**：
- `type: str` 是判别字段；
- `_subclass_registry: ClassVar[dict[str, ...]]` 在 `__pydantic_init_subclass__` 时登记；
- `parse(payload)` 按 `type` 找回具体 options 类；
- `_serialize_always_include_type` 保证序列化**永远带 `type`**。

> Rust 落点：这是 serde 的 `#[serde(tag = "type")]` 内部标记枚举＋注册表二选一。注册表在 Rust 里要么用 `inventory`/`linkme` 静态注册，要么由宿主显式装配。**建议显式装配**（宿主把支持的后端登记进一张表），因为链接期注册会让「支持哪些后端」随 feature 组合漂移。

### 3.2 `BaseSandboxSession` / `SandboxSession`

两层：`BaseSandboxSession`（`abc.ABC`，后端实现它）与 `SandboxSession`（在其上加事件、trace、限流、路径校验的**装饰层**）。只有一个 `@abc.abstractmethod`：`_exec_internal`。其余都是带默认实现的模板方法钩子。

生命周期以 `BaseSandboxSession` 的实际控制流为准，不能简化为无条件串行链：

| 操作 | 成功路径 | 分支与失败语义 |
| --- | --- | --- |
| `start()` | 先校验 mount credential boundaries；进入 try 后依次 `_ensure_backend_started`、记录 `workspace_root_ready`、`_probe_workspace_root_for_preserved_resume`、`_prepare_backend_workspace`、`_ensure_runtime_helpers`、`_start_workspace`；成功后 `_after_start`，最后设 `workspace_root_ready=True` | **探测先于准备**，避免把新建目录当成恢复证据。try 内 `Exception` 才走 `_after_start_failed` 与 `_wrap_start_error`；前置校验和 try 外 `_after_start` 的失败不经过该分支。不得擅自把取消异常与普通异常归为同一种捕获。 |
| `_start_workspace()` | 再校验挂载边界，然后按 snapshot 与 workspace 是否保留选择路径 | snapshot 可恢复且 fingerprint/manifest 允许复用：只重建 ephemeral；可恢复但不能复用：恢复 snapshot 再重建 ephemeral；无可恢复 snapshot 但工作区确认保留：只重建 ephemeral；其余：完整物化 manifest。`_restore_snapshot_and_reapply_ephemeral_on_resume` **不是每次 start 必经步骤**。 |
| `stop()` | 前置挂载校验后 `_before_stop`（默认终止 PTY）→ `_persist_snapshot` | try 内失败走 `_wrap_stop_error`；进入 try 后 `_after_stop` 在 **finally** 执行，持久化失败也执行。前置校验失败尚未进入该 finally。stop 是持久化阶段，不等于关闭后端。 |
| `shutdown()` | `_before_shutdown`（默认终止 PTY）→ `_shutdown_backend` → `_after_shutdown` | 顺序 await，没有把后两步放 finally；前一步失败会跳过后续。 |
| 直接 `aclose()` | 取得关闭锁后 `_aclose_impl`：pre-stop hooks → 条件 stop → shutdown → finally 关闭 dependencies；不自动调用 client.delete | hooks 失败记录首个错误，跳过 stop，仍尝试 shutdown；**stop 失败时跳过 shutdown**，但仍关闭 dependencies 并抛首个记录错误。重复关闭／hooks 失败粘性按源码和测试移植，不另作幂等假设。 |
| Runner-owned cleanup | 由 `_SandboxSessionResources.cleanup` 执行，不能直接以 `aclose` 替代 | borrowed 直接返回；owned 受锁与 `_cleaned` 保护：hooks 失败跳过 stop；stop 失败仍尝试 shutdown；finally 尝试符合条件的 client.delete，最后关闭 dependencies；保留首个错误。 |

`SandboxSession` 装饰层转发到 inner；生命周期错误的挂载信息脱敏也必须保留。上面两种关闭入口的差别是固定基线的事实，若将来跟随上游修复，应单独升级基线，不能在移植时悄悄统一。

**能力探测**两个：`supports_pty()`、`supports_docker_volume_mounts()`——工具装配直接读它们。

对外操作面：

| 族 | 方法 |
| --- | --- |
| 执行 | `exec(*command, timeout, shell=True, user)` → `ExecResult`；内部 `_prepare_exec_command` → `_exec_internal` |
| PTY | `pty_exec_start`、`pty_write_stdin`、`pty_terminate_all` |
| 文件 | `ls`、`rm`、`mkdir`、`read`、`write`、`normalize_path`、`_validate_path_access` |
| 归档 | `persist_workspace()` → `io.IOBase`、`hydrate_workspace(data)` |
| 端口 | `resolve_exposed_port(port)` → `ExposedPortEndpoint` |
| Manifest | `apply_manifest(only_ephemeral=False)` → `MaterializationResult` |
| 状态 | `running()`、`state` property |
| 依赖 | `dependencies()`、`set_dependencies()`、`register_pre_stop_hook()` |

`exec` 的默认 `shell=True` 语义写在 docstring 里：**前缀 `sh -lc`**；传 list 可换前缀。这是 `login` 语义的真正来源。

### 3.3 `SandboxSessionState`（`session/sandbox_session_state.py`）

公共字段八个，同样用 `type` 判别 ＋ `_subclass_registry`：

```
type: str
session_id: uuid.UUID          # 默认 uuid4
snapshot: SerializeAsAny[SnapshotBase]
manifest: Manifest
exposed_ports: tuple[int, ...] # 默认空
snapshot_fingerprint: str | None
snapshot_fingerprint_version: str | None
workspace_root_ready: bool     # 默认 False
```

三个私有属性影响恢复安全：`_path_grants_require_rebind`、`_mount_authority_redacted`、`_mount_authority_rebound`。**恢复时挂载凭据要重新绑定而不是从 state 里读回**——这条直接决定序列化格式，必须移植，不能简化。

### 3.4 `types.py`

| 类型 | 形态 | 要点 |
| --- | --- | --- |
| `User` | `{name: str}` | 按 name 做 hash/eq |
| `Group` | `{name, users: list[User]}` | 按 name 做 hash/eq |
| `Permissions` | `{owner=0o7, group=0, other=0, directory=False}` | `to_mode` / `from_mode` / `from_str`；`from_str` 要处理 `ls` 的 ACL/xattr/SELinux 尾标 `+ @ .`，并认 `s/S/t/T` |
| `FileMode` | IntEnum | `ALL=0o7, NONE=0, READ=4, WRITE=2, EXEC=1` |
| `ExecResult` | `{stdout: bytes, stderr: bytes, exit_code: int}` ＋ `ok()` | **stdout/stderr 是分开的 bytes** |
| `ExposedPortEndpoint` | frozen `{host, port, tls=False, query=""}` ＋ `url_for(scheme)` | 只认 `http`/`ws`；IPv6 加方括号；默认端口省略 |

> `Permissions.owner` 默认 `0o7`（rwx）而 group/other 为 0——**默认是 0700 语义**，与 Rusty `RunTempDir` 的 `0o700` 巧合一致，但那是两回事，不能互相引证。

### 3.6 当前 Rust 增量的验收边界（2026-09-16）

截至首个增量，`ra-core::sandbox` 交付值类型、错误码与错误载荷，**不代表 R8-P1 全部完成**。Client/Session/State、具体 options/state 注册、依赖容器、生命周期装饰层和恢复授权重绑定仍待移植，不能用本增量的测试替代这些验收。后续注册机制增量见 §3.7。

本次审核修复：

- `Permissions` 反序列化省略字段时复用 `Default`（0700、非目录）；`ExposedPortEndpoint` 的 TLS/query 同样保留上游缺省值。
- `owner_can/group_can/others_can` 接受 `FileMode` 或 `u32` 掩码；位或组合返回 `u32`，支持读写、读执行等组合。Rust 的数值掩码使用 `0o6_u32` 等显式类型；builder 消费并返回值，适配 Rust 所有权，不模拟 Python 可变对象别名。
- Python 异常继承用 `ErrorCode` + `SandboxErrorDetails` 表达；`exec_nonzero/exec_timeout/exec_transport/pty_session_not_found` 保留类型化载荷，原始输出字节与供人阅读的有损 UTF-8 context 分开保存。context 覆盖不修改类型化载荷。
- 端口及常用 workspace 错误提供具名构造入口。通用 `SandboxError::new` 仍是低层入口；其余上游异常的具名构造与调用点迁移未宣称全部完成。
- Rust builder 的重试属性在读取时回退到直接 sandbox cause，因而通过 `with_cause` 或 `with_sandbox_cause` 设置原因一致，显式 `Some(bool)` 优先；`None` 表示继承原因或保持未知。此做法适配 Rust 分步构造，避免 setter 调用顺序改变最终语义。

验证：`cargo test --manifest-path tests/it-core/Cargo.toml --test sandbox_contract`，35 项通过；`cargo clippy -p ra-core -- -D warnings` 通过。

### 3.7 注册机制与 Snapshot 值对象增量（2026-09-17）

新增的是显式 `TypeRegistry`、原始 `DiscriminatedPayload` 与最小 `Snapshot` 值对象。`client_options_kind/session_state_kind/snapshot_kind` 仅区分注册表家族和错误策略；不是具体 options/state 的实现，也没有实现挂载授权清理或重绑定。`BaseSandboxClient`、`BaseSandboxSession`、`Manifest`、`SandboxSessionState` 及 state 往返仍未交付；Snapshot 的 IO 行为归 P7（local／noop 随 §3.11，生命周期接线随 §3.12）。

审核修复与 Rust 表达差异：

- 扩展字段不能覆盖 `type`；与 Snapshot 的 `id` 一样，写入保留键的 builder 调用不修改值。序列化最后写入权威 discriminator，normalizer 也不能改成另一种类型。
- state 家族的未知类型和校验失败错误不保留原始 discriminator、验证器 reason 或 source；`Display` 和 `Debug` 都不携带这些敏感数据。非脱敏家族仍保留诊断详情。
- `DiscriminatedPayload` 明确是可构造、可反序列化的未校验数据。`readmit` 重新执行注册验证器，不能照搬上游“已构造的具体模型直接返回”的捷径，因为该原始载荷没有同等的构造校验保证。
- `Snapshot` 保留 `Serialize`，移除无需注册表的 `Deserialize` / `TryFrom<Value>`，`from_payload` 改为私有。持久化恢复先读为 JSON，再调用 `Snapshot::parse(&registry, &value)`，确保未知类型拒绝和具体类型 normalizer 都生效。`new/with_field` 用于受信任的后端配置构造，不是持久化恢复入口。这是显式注册表不能通过普通 serde `Deserialize` 隐式传入所需的适配，没有引入全局注册表。

回归覆盖：保留键覆盖、state 错误的 Display/Debug/source 脱敏、构造／反序列化／修改后 readmit 的验证、接收方 normalizer、Snapshot 经注册表恢复与往返、normalizer 改换类型的拒绝；另有编译失败文档测试防止恢复无注册表的 Snapshot 反序列化入口。

**线格式已用上游实测逐项核对**（`Manifest.model_dump(mode="json")` 与 `describe()`）：条目平铺字段与默认权限 0755（目录型 `directory=true`）、`git_repo` 的 `host/ref/repo/subpath`、`local_dir` 的 `src: null`、`file.content` 为 UTF-8 字符串且非 UTF-8 上游同样报错；挂载的 `mount_path/read_only/mount_strategy`、`pattern.options` 嵌套、`docker_volume.driver_options`；环境的 `{"value": {...}}` 包一层与 `EnvEntry` 的三字段；`describe(depth=1/2/None)` 的树形输出逐行相同。

Rust 表达差异（每条都注明必要性）：

- **`WorkspacePathPolicy` 只移植 POSIX（远端）那一半。** 上游同一个类里还有一条跟随宿主符号链接的路径（`resolve_symlinks`、`root_is_existing_host_path`、`sandbox_path_grant_host_path` 的 `resolve()`），那需要读真实文件系统；`ra-core` 不做 IO 是 §8 的分层裁决。**词法检查不能替代它**：工作区内的符号链接可以指向工作区外，只有解析型检查能发现。该半边随 P3 的 unix-local 落地。
- **`PosixPath` 在构造时按 `PurePosixPath` 的规则整理拼写**：合并重复分隔符、丢掉单独的 `.`、去掉尾部分隔符，保留恰好两个前导斜杠，**但不动 `..`**。不整理会让 `resolve_workspace_path("/w", "./README.md")` 产出 `/w/./README.md`、`anchor("./plot.png")` 产出 `tasks/a/./plot.png`，与上游不一致。解析 `..` 是 `normalized()`，仍与构造分开。
- **`Manifest` 去掉 `Deserialize`，改用 `Manifest::parse(&registry, &value)`。** 条目类型是开放家族，普通 serde 反序列化传不进注册表。与 §3.7 的 `Snapshot` 同一处理。`Environment::parse` 另收一张 env value 注册表，两张表分开是因为家族本来就是两个。
- **`Dir.children` 与 `Manifest.entries` 用 `BTreeMap`（按名排序），不是插入序。** `iter_entries` 仍是前序。上游的插入序不被任何语义依赖（`describe` 自己排序、`ephemeral_entry_paths` 是集合、物化是并发的）。
- **`MountPattern` 是闭合枚举，`MountStrategy` 与 `MountProvider` 开放。** 上游 `pattern` 字段就是四选一的判别联合（未注册的工具直接拒），而 `MountStrategyBase` 和 `BaseEntry` 有子类注册表。三者的开闭跟着上游走。
- **挂载权限位不生效，Rust 直接固定而不告警。** 上游 `warnings.warn` 后覆盖；没有任何值会被兑现，日志只是把一次无效配置写进流水。文档写明访问控制在 provider 侧配置。
- **`Environment::resolve` 的兄弟取消由 combinator 提供。** 上游需要专门的 `gather_with_cancel`，因为 `asyncio.gather` 出错即返回、剩余任务仍在跑；Rust 里 `try_join_all` 出错即被丢弃，丢弃 future 就是取消。语义相同，不另写并发原语。
- **`GitRepo` 的 `ref` 字段在 Rust 叫 `reference`**（`ref` 是关键字），线上仍写 `ref`。
- **`EntryContent::Mount` 装箱**：挂载带着整套 provider 凭据字段，不装箱会让每个条目都按最大的挂载算大小。
- **截断的定点搜索加了 8 轮上限。** 标记文本里写着被丢掉多少字符，它自己的长度又取决于那个数字；上游的循环没有出口，相差一位数字的两个长度可以互相换位。到上限就采用最后一次测量。
- **不做截断日志。** 上游 `logger.warning`；截断本身已经写在输出里（而且是给模型看的那句），比日志更有用，`ra-core` 也不引入日志副作用。
- `PathGrantError` 新增 `NotAGrant`／`PathMissing`／`FieldType`：上游由 pydantic 的必填与类型校验报出，Rust 手写读取需要自己命名这三种；其余六条错误文案与上游逐字相同。
- **渲染省略空集合**（entries／environment／users／groups／extra_path_grants）。上游一律写出空集合。两边所有字段都有默认值，互相都读得进；差别只在空 manifest 写多少字节。此为前一批已有的取舍，本批沿用未改。

- **客户端构造拆成三个函数。** 上游 `__init__` 有两种运行期错误：给了 allowlist 却没关继承、allowlist 传了字符串。前者在 Rust 里「指定 allowlist」本身就意味着关继承，后者参数是 `IntoIterator<Item = String>`，`&str` 不满足。两条错误因此**不可表达**而不是不移植；对应的上游测试没有 Rust 对照物。

- **宿主路径解析改为可失败的 `Result<PathBuf, SandboxError>`。** Python 可通过异常报告循环；Rust 必须显式把错误传到调用者，不能把未解析完的路径当作授权结果。`HostWorkspacePaths::new` 与 `sandbox_path_grant_host_path` 同步返回 `SandboxError`，根、grant、普通路径、exec 围栏和归档恢复均传播解析失败。合法长链完整解析，不设置固定层数上限；缺失路径仍保留，支持新文件写入。循环与无法完成授权解析的 IO 错误返回 `SandboxConfigInvalid`（exec／归档入口再包装为各自错误）。这是服务层的错误表达；部分 Python 版本的 non-strict resolve 会保留循环或不可访问分量，本实现明确拒绝此类未完成解析，避免把残余符号链接交给后续 IO 继续跟随。
- **路径策略不缓存。** 上游按 `(root, grants)` 缓存 `WorkspacePathPolicy`；这里每次重建，因为 manifest 在锁后面、生命周期会写它，缓存键一旦过期就是在回答上一份 manifest 的问题。
- **归档成员名没有 `./` 前缀。** 上游 `tar.add(root, arcname=".")` 产出 `./src/main.rs`，`tar` crate 写入时会去掉这个前缀，成员名是裸相对路径。互读没问题（上游 `_tar_member_rel_variants` 两种都认，本侧解析时丢掉 `.` 分量），但**同一个工作区两边产出的字节不同**，跨实现比指纹时要知道这一点。
- ~~**删除工作区时，manifest 声明了挂载就整个不删。**~~ 已随 P2 第二批改为上游行为（§3.19）：先 `unmount` 每个 ephemeral 挂载，有一个失败就不删根。in-container 的 pattern 命令尚未移植，所以这类挂载目前仍走「卸载失败」分支。
- **`create` 不提前拒绝声明了账号的 manifest。** 上游只在物化与 `provision_manifest_accounts` 里拒；提前到 `create` 会让本 client 拒掉上游允许持有的配置（同一份 manifest 可以交给容器后端）。

Rust 表达差异（每条注明必要性）：

- **`apply()` 不挂在 `Entry` 上，改由 `ra-sandbox` 按 `EntryContent` 分派。** §3.8 已裁决 `ra-core` 只放声明、不做 IO；把 `apply()` 挂回条目会让 `ra-core` 直接依赖文件系统与 `SandboxSession`。代价是**宿主注册的条目类型（`EntryContent::Extension`）没有物化实现**——manifest 解析得进来，物化时明确拒绝而不是静默跳过。这是本批的已知缺口，不是裁决。
- **`only_ephemeral` 拆成两个方法。** 上游一个方法两个旗标，而公开入口永远传 `provision_accounts=not only_ephemeral`；四种组合里只有两种存在，拆开后写不出第三种。
- **`_prune_to_ephemeral` 没有对应物。** 上游只在 `artifact.ephemeral` 为真时调它，而它开头两个分支就把这种输入全接走了，剪枝体不可达。Rust 侧实现的是可达行为：**ephemeral 目录整棵重建，包含其中非 ephemeral 的子项**（上游 `test_manifest_applier_only_ephemeral_reapplies_full_ephemeral_directories` 断言的就是这个），已选中路径的后代跳过。
- **`gather_in_order` 使用带序号的 `buffer_unordered`。** 按完成顺序观察首错并取消同批 future，成功结果按输入序号恢复顺序；已完成的条目立即释放并发名额，不被前面的慢条目阻塞。对应上游 `FIRST_EXCEPTION` 与 worker 持续领取下一项的行为。
- **Git 清理由独立 Tokio task 持有会话并执行。** `ManifestApplier::new` 接收 `Arc<dyn SandboxSession>`；本地 session 的内部句柄共享 state 和 running 标志。Rust 的 future drop 无法执行异步 `finally`，因此检出 task 在调用方取消时停止当前操作、再执行 `rm`；批次错误返回前等待所有检出清理。调用方直接丢弃整个 application future 时，清理继续运行于当前 Tokio runtime，调用方无法同步等待它；runtime 必须保持运行。正常错误仍沿用上游的清理顺序和错误优先级。这是 Rust 异步所有权的必要适配，不把额外策略塞进 provider-neutral core。
- **本地 exec 在取消时终止整个进程组。** 参考 codex 的进程组回收机制，以 drop guard 在 Git 清理启动前发送 SIGKILL，并让 Tokio 回收直接子进程；避免取消后 clone/cp 继续写入。这里使用立即终止，未引入 codex 产品层的 TERM 宽限期配置。
- **只移植钉住目录句柄的那条遍历路径。** 上游另有不带 `dir_fd` 的回退实现给没有 `openat` 的平台；本批 `materialize` 模块和 unix-local 后端都受 `cfg(unix)` 保护，crate 的其余声明与工具仍可在非 Unix 平台编译。
- **目录条目里按名排序。** `list_files` 对结果排序：上游按文件系统返回顺序拷贝，回执顺序因此随目录实现变化；回执是给人对账的，同一棵源目录两次跑应当得到同一份。
- **拷贝走内存而不是流。** `SandboxSession::write` 收 `Vec<u8>`（既有形状），所以一个文件是读满、算 sha256、再写；上游 `seek(0)` 复用同一个句柄。单文件大小因此受内存约束，这一条随 write 的流式化一起改。

- **取消清理是本移植独有的一层，上游不需要。** 上游 `GitRepo.apply` 把 `rm -rf` 放在 `finally` 里，asyncio 取消一个协程时那段照样跑完；**Rust 丢弃一个 future 不会 await 任何东西**，而 `gather_in_order` 首错即丢弃兄弟任务，所以照抄「`finally` 里删」会让一次失败的批次留下 `/tmp/sandbox-git-…` 和一个仍在写的子进程。三处改动合起来补这个洞：①`ManifestApplier` 持 `Arc<dyn SandboxSession>` 而不是借用，检出才能搬进一个能活过调用方的 `tokio::spawn`；②该 worker 用 `select!` 监听一个 drop 信号，无论完成还是被取消都执行同一句删除，句柄进 `CleanupTasks`，`apply_entries` 在返回前 `wait()`——物化报完成时清理一定已经结束；③`unix_local::exec::run` 加 `kill_on_drop(true)` 与 `ProcessGroupGuard`，被丢弃的 exec 在清理开始前先杀掉整个进程组，这正是 worker 那句删除能成立的前提（否则删完还会被重新创建）。验收在 `manifest_application::{dropping_an_application_cancels_checkout_and_finishes_cleanup, a_batch_failure_waits_for_cancelled_checkout_cleanup, a_later_failure_cancels_an_earlier_pending_entry}` 与 `unix_local_exec::dropping_exec_stops_descendants_before_they_can_write_again`。
- **拷贝目录途中的 IO 失败报 `local_dir_read_error` / `local_checksum_error`，上游报 `local_file_read_error`。** 上游这个分叉来自 `except OSError` 捕不到自家的 `LocalDirReadError`，是异常层级的副产物。**调用方真正分支用的那四种拒绝——`symlink_not_supported`、`path_changed_during_copy`、`outside_base_dir`、`path_not_found`——两边错误码与 `reason` 完全一致**，`local_file` 那条路径的重包装（丢掉 `src`、保留其余 context）也逐字照移。
- **限额由 client/session 在构造时接收。** 上游从 run config 取、在 session 建好之后调 `_apply_concurrency_limits`；run config 归 P4 未移植，所以暂时挂在 client 上（与环境策略同理：这是跑 SDK 的进程对自己机器的决定）。P4 接线时换成传一个 `SandboxConcurrencyLimits`，不再新增两个数字。
- **`SandboxConcurrencyLimits` 放在 `ra-core::sandbox::materialization` 而不是 run config 模块。** 它是它约束的那个结果类型的邻居，而 run config 这个模块还不存在；零值用 `ConcurrencyLimitError` 拒绝，对应上游 `__post_init__` 的 `ValueError`。

**本批未移植、明确留给后续的**：

| 缺口 | 归属 |
| --- | --- |
| ~~挂载条目的物化（`Mount.apply`、`MountPattern.apply/unapply`、rclone 配置合成）~~ | **已交付，见 §3.19／§3.20** |

**两条本后端上的事实，值得单独记，因为它们会让人以为移植漏了东西**：

Rust 表达差异（每条注明必要性）：

- **三件 IO 挂在 `SnapshotStore` 上，不挂在快照对象上。** 上游靠子类给快照加存储，而这里的快照是要随 state 序列化的数据——从磁盘读回来的载荷本来就得重新找实现。所以宿主的扩展点从「继承 `SnapshotBase`」换成「实现 `SnapshotStore`」。代价是 `BuiltinSnapshotStore` 认不得的类型一律拒绝而不是静默当空，和 §3.10 的 `EntryContent::Extension` 同一处理。
- **收发整段字节，不收发流。** `SandboxSession::{persist_workspace,hydrate_workspace}` 已经是 `Vec<u8>`（§3.9 的既有形状），上游用 `shutil.copyfileobj` 分块拷。因此上游「拷到一半 `read()` 抛错」那条原子性用例在 Rust 里不可表达，改用「目录不可写」触发同一条清理路径：旧快照原样、临时文件不留。两者验的是同一个保证。
- **`base_path` 不是 UTF-8 就拒绝，`Snapshot::local`／`SnapshotSpec::build`／`resolve_snapshot` 因此可失败（`SnapshotPathError`）。** 上游的 `Path` 随对象一起活在进程里，不需要编码；这里它要进 JSON 载荷、随 state 落盘。**最初写的是 `to_string_lossy()`，那是个会丢数据的 bug**：非法字节一律变成同一个 U+FFFD，于是两个只在这些字节上不同的目录会映射到同一个存储位置——审核实测复现了「先后用同一个 id 存两次、恢复第一个拿到第二个内容」。改成显式拒绝：`SnapshotSpec::Local` 的字段是公开的，所以 `build` 是最后一道能挡住它的地方。`ra-sandbox::snapshot::defaults::resolve_default_local_snapshot_spec` 同理——默认目录由账号 home 拼出来，非 UTF-8 的 home 在建目录之前就报 `SandboxConfigInvalid`，不把一个用不了的 spec 交出去。回归用例 `sandbox_snapshot::two_directories_that_differ_only_in_unreadable_bytes_cannot_name_the_same_storage` 钉住两条路径的 lossy 渲染确实相同、而三个入口都拒绝。
- **id 单段校验写成显式规则，不借 `PurePosixPath`/`PureWindowsPath`。** 规则是实测对齐上游两种拼写后得到的：空、`.`、`..`、含 `/` 或 `\`、开头 `<ASCII 字母>:` 一律拒。**`:a`、`ab:c` 这类上游接受的名字这里同样接受**——盘符要求冒号前恰好一个字母，把它们一起拒掉会比上游更严，有回归用例钉住。
- **`ValueError` 变成 `SandboxConfigInvalid`。** Rust 没有那条异常通道；错误码取配置类，消息保留 `single path segment` 这半句，三个操作（persist/restore/restorable）都在用路径之前拒绝，与上游 `_path()` 的位置一致。
- **`HostPlatform` 三分支代替 `sys.platform` ＋ `os.name` 两个字符串。** 上游四个 keyword-only 参数里只有三种组合描述真实宿主；`SnapshotHost` 把 home／env／platform 一起显式传入，Windows 分支因此在 macOS 上也有实测，而不是只在 Windows 上才跑到。
- **默认目录是 `rusty-agent/sandbox/snapshots`，上游是 `openai-agents-python/sandbox/snapshots`。** 这是用户账号下本产品自己的 state 目录，不是互读格式；照抄上游的发行包名会让两套 SDK 的归档混在一处。
- **UNC 判定在本模块自己实现。** `ra-core` 的 `windows_absolute_path`（§3.8 的既有形状）只认盘符，因为它的调用点先拒反斜杠；而 `%LOCALAPPDATA%` 允许 `\\server\share`，上游 `PureWindowsPath.is_absolute()` 认它。实测确认的规则是「恰两个分隔符 ＋ 非空 server ＋ 非空 share」，`\\server`、`\\server\\share`、`///server/share` 都不算。没有改 `ra-core` 那个函数：它的语义由 P2 的调用点定义，改它会波及 cwd 与授权判定。
- **`max_age_seconds < 0` 的早退不可表达。** `Duration` 非负；`now.checked_sub(max_age)` 溢出时仍然早退，对应上游「时间算不出来就什么都不删」的那一半。
- **建目录失败报 `SnapshotPersistError`。** 上游直接把 `OSError` 抛给调用方；Rust 侧要一个 sandbox 错误码，取了它所属的那一族，消息写明是默认目录。

**本批未移植、明确留给后续的**：

| 缺口 | 归属 |
| --- | --- |
| ~~`RemoteSnapshot` 的 persist/restore/restorable（`_require_client_method` 的鸭子类型检查与 `<remote:key>` 路径）~~ | **已交付，见 §3.15** |
| ~~snapshot 生命周期接线：`session/snapshot_lifecycle.py`、`_clear_workspace_root_on_resume`、指纹计算与缓存~~ 已交付，见 §3.12；`tar_workspace.py`、`workspace_payloads.py`、`archive_extraction.py` 仍未移植 | P7 第二批已交付（见 §3.12）；其余见该节的未移植表 |

Rust 表达差异（每条注明必要性）：

- **生命周期落在服务层，不落在 `ra-core` 的默认方法里。** 上游写在 base session 上，而这里它要调 store（真实 IO），`ra-core` 不做 IO。处理方式与 §3.10 的 `ManifestApplier` 一致：协议留钩子，服务层给实现，后端 session 把钩子转过去。Docker（P8）复用同一个模块，这正是上游把它放在 base session 上想要的效果。
- **指纹写回 state 走一个钩子，不直接改字段。** 上游 `session.state.snapshot_fingerprint = …`；这里 `state()` 返回副本（§3.3 的既有形状），所以新增 `record_snapshot_fingerprint(Option<SnapshotFingerprint>)`，与既有的 `record_workspace_root_ready` 同形。**`None` 是有意义的值**：这次 persist 没算出指纹，就必须把上一次留下的抹掉，否则下一次 resume 会拿旧指纹去比一个新工作区。
- **helper 安装不做每 session 缓存。** 上游记一份已装集合，命中时跑 `test -x` 探一次——**和直接跑安装脚本一样是一条命令**，因为安装脚本本身就是幂等检查（内容相同就原样退出）。所以不移植那份缓存，连同只有容器后端会用的 `_current_runtime_helper_cache_key` 失效键。
- **指纹脚本是重写的，不是拷贝的。** 逐条保留上游行为：参数契约、排除路径必须是具体相对路径、每条排除两种拼写、`--no-wildcards` 与「转义通配符」两条分支、`sha256sum`／`shasum`／`openssl` 依次尝试、缓存经临时文件再 `mv`。**一处有意不同**：打包用 `sh -c` 而不是上游的 `sh -lc`——登录 shell 会先跑 profile，它打印的任何东西都会混进被哈希的那条管道里。
- **`/tmp/rusty-agent/{bin,session-state}` 而不是 `/tmp/openai-agents/…`**，理由同 §3.11 的默认目录：沙箱里属于本 SDK 的 scratch，不是互读格式。
- **`_should_compute_snapshot_fingerprint_on_persist` 没有对应物。** 上游是私有钩子，默认 `True`，全仓没有任何实现覆盖它；需要时再加，不先造一个没有第二种答案的开关。
- **`read_cached_snapshot_fingerprint` 未移植**：上游除 base session 的一层转发外没有调用者。
- **「列目录失败＝这里没东西」按错误码判定。** 上游只吞 `ExecNonZeroError`；本地 `ls` 报的是 `WorkspaceReadNotFound`／`WorkspaceRootNotFound`／`ExecNonzero` 三者之一，都按「当作空目录，后面的恢复会自己建」处理，其余错误照常上抛。
- **`snapshot_fingerprint_cache_path` 不分两支**：上游按「根是不是宿主实路径」选 `Path` 的两种风味，在 POSIX 上产出同一个字符串，而沙箱内的路径本来就是 POSIX。
- **manifest 摘要与上游不保证逐字节相同。** 两边都是排序键的紧凑 JSON，但字段渲染未必逐项一致。只影响在两套实现之间搬运的 state，且失配方向安全：摘要不同 → 指纹不同 → 恢复，而不是跳过恢复。

**审核修复（2026-09-22）**：

- 恢复前清理改走 `SandboxSession::remove_workspace_entry_on_resume`。默认沿用 `rm`；unix-local 覆盖为验证并解析父目录后删除叶子本身，避免普通 `rm` 解析叶子链接、删除目标而遗留链接。普通文件 API 的上游语义保持不变。新增钩子是本地恢复清理所需的 Rust 后端适配，真实 session 回归覆盖内部、外部和悬空链接，并确认外部目标未被删除。
- 指纹脚本修复上游同样存在的管道状态缺陷：POSIX `sh` 只返回管道最后一个命令的状态，原来 tar 失败也会给空流或部分流计算有效指纹。现在通过私有临时目录内的失败标记确认 tar 成功，仍保持流式归档；哈希命令独立检查退出状态。任一步失败都不输出有效记录、不覆盖旧缓存，临时状态在退出时清理。这是明确的上游缺陷修复，不是新增产品策略。回归覆盖 tar 空输出失败、部分输出失败及哈希失败，每种均验证无缓存和已有缓存两种情况。

**三条值得单独记的事实**：

1. **macOS 上指纹算不出来，这是上游同款行为。** helper 装在 `/tmp`，而本后端（与上游）的 `sandbox-exec` profile 把 `/tmp` 与 `/private/tmp` 列在那 12 条 deny 里（§3.9／§3.10 已记）。所以 macOS 上每次 stop 都是「归档存了、指纹没有」，resume 一律恢复。**本机实测走的就是这条路**：`unix_local_snapshot::a_stop_stores_the_workspace_whether_or_not_it_could_hash_it` 取到 `None` 分支，并顺带断言 helper 根目录确实不可写——证明缺指纹是围栏造成的，不是实现漏了。**Linux 上算得出指纹的那条分支没有实测记录。** 脚本本身另有一组测试用 `sh` 直接跑过（安装幂等、哈希、缓存、排除生效、拒绝越界排除、根不存在），不经过沙箱。
2. **skip-restore 分支在 unix-local 上走不到**，与 §3.10 的 `reapply_ephemeral_manifest` 同理：协议只在「工作区内容跨停机保留」时问它，而本后端 `workspace_state_preserved_on_start()` 取默认 `false`（上游 unix_local 同样从不调 `_set_start_state_preserved`）。实现它是因为 persist 已经在记指纹，而没人读的指纹会慢慢变成假的；验收用录制 session。
3. **指纹是对 tar 流算的，所以文件元数据算数。** 把同样的字节重新写一遍会得到新的 mtime，因此是新的指纹，resume 于是恢复而不是跳过——安全方向，且上游哈希的是同一个归档，行为一致。用例 `runtime_helpers::the_answer_is_about_the_archive_not_only_the_bytes_in_it` 把这点钉住。

**本批未移植、明确留给后续的**：

| 缺口 | 归属 |
| --- | --- |
| ~~`register_persist_workspace_skip_path`（运行期追加排除路径，含与挂载重叠的拒绝）~~ | **已交付，见 §3.19** |

Rust 表达差异（每条注明必要性）：

- **只认未压缩 tar。** 上游 `tarfile.open(mode="r|*")` 顺带解 gzip／bz2／xz，`tar` crate 不解压，所以一个内容其实是 gzip 的 `.tar` 在这里报「unreadable archive」。**这是本批缺口，不是裁决**；补它要引入 `flate2` 之类的新依赖。既有的 `hydrate_workspace` 同样只认未压缩 tar，之前没记，一并记在这里（hydrate 这一半已随 P3 收尾补上，见 §3.21）。
- **zip 明确拒绝。** 上游支持，这里需要新的第三方依赖（`zip` crate），而引依赖是产品决定，留作单独一次。当前报 `SandboxConfigInvalid` 并在消息里写明未移植，**不伪装成「非法 scheme」**——后者会让调用方以为自己传错了。
- **成员字节按区间切片，不持有 tar reader。** `tar::Archive` 不是 `Sync`，而每次写入都是 `await`；头部那一遍顺手记下每条成员的数据区间（`raw_file_position` ＋ size），写入时按区间切片。等价于上游读两遍，且不会把整包成员同时留在内存里。
- **归档本体多一次 `clone`。** `SandboxSession::write` 收 `Vec<u8>`，而解压还要用同一份字节；上游把它 spool 到磁盘一次再复用句柄。随 write 的流式化一起改。
- **限额零值在构造时拒绝**，上游在 `validate()`／`__post_init__` 里拒；负数在 `u64`／`usize` 下不可表达，与 `SandboxConcurrencyLimits`（§3.10）同形。
- **`_validate_path_access` 移植为 `SandboxSession::validate_path_access`。** 默认采用 manifest 的词法路径策略；unix-local 覆盖为宿主路径解析与授权，并拒绝无法无损表示为 UTF-8 的解析结果。格式仍按调用方提供的名字推断，随后先解析归档路径，再取解析后的父目录作为解压根，与上游顺序一致。每个文件操作继续执行自身授权检查。
- **三个中间异常没有对应物。** `UnsafeTarMemberError`／`UnsafeZipMemberError`／`ArchiveResourceLimitError` 在上游只是为了被 `except` 重新包成 `WorkspaceArchiveWriteError`；这里直接构造那个错误，`reason`／`limit`／`actual`／`member` 四个 context 键逐字保留。

### 3.14 R8-P7 归档格式补齐（2026-09-23）

`ra-sandbox::archive::WorkspaceArchiveExtractor` 现在按上游 `archive_extraction.py` 接受 zip 以及 gzip、bzip2、xz 压缩的 tar。格式仍按最后一个扩展名或显式 `CompressionScheme` 决定；例如 `.tar.gz` 仍须显式指定 `Tar`。zip 的路径、链接、重复成员、穿过文件的路径、成员数与解压字节限额在写入成员前校验，写入仍走 session API。压缩 tar 与上游 `tarfile.open(mode="r|*")` 一样边解码边校验：头部校验直接跑在解码流上，超限在解压出内容前就拒绝；通过后只解码到最后一个成员内容结束处，归档结束标记之后的数据不再解码。zip 链接成员与上游一样取外部属性高 16 位判定，不看生成系统（`zip` crate 的 `unix_mode` 会把 DOS 生成的成员一律报成普通文件），并排在路径规则之后，同时越界又是链接的成员报「parent traversal」；`zip` crate 按成员名建索引，同名的第二个条目会静默覆盖第一个、绕过逐成员校验；因此另行遍历中央目录原始条目；发生同名折叠时，按原始顺序逐条检查路径、外部属性、成员数、声明大小及路径冲突。重复目录也逐条计入限额，只有通过校验后才允许；隐藏在后续同名目录之前的链接不能跳过检查。原始名称按 UTF-8 标志或 CP437 解码，ZIP64 声明大小从扩展字段读取，根条目仍按上游先跳过。名称解码不限于发生折叠时：逐成员校验也从中央目录的原始字节按同一规则解码，不用 `zip` crate 给出的名称——它不在 NUL 处截断，而上游 `ZipInfo` 截断，所以只在 NUL 之后不同的两个名称是同一路径（已用 Python 3.11 实测）。`zip` crate 对标了 UTF-8 的非法名称做有损替换，上游则抛 `UnicodeDecodeError`（属 `ValueError`，转为归档写入错误，已实测）；这一条原本就由每次都执行的原始条目遍历拒绝，逐成员解码只是不再依赖那一步。zip 成员按中央目录声明的大小计限额，写入时最多读声明大小加一字节，实际内容与声明不符即拒绝（上游 `ZipExtFile` 读满 `file_size` 即停，`zip` crate 不做这个截断，所以由 Rusty 自己补上）。

引入 `zip`、`flate2`、`bzip2`、`lzma-rust2` crate，解压全走纯 Rust 实现：`bzip2` 打开 `libbz2-rs-sys` 后端（经特性合并也覆盖 `zip` 的 bzip2，`bzip2-sys` 以 `__disabled` 跳过 C 构建），xz 用 `lzma-rust2` 的 `XzReader` 而非绑定 liblzma 的 `xz2`，使用单流模式，对齐上游实际调用的 `tarfile.open(mode="r|*")`：该入口只使用一个 `LZMADecompressor`，不会继续读取第二个 xz 流来补齐截断的 tar。gzip 同理用单成员的 `GzDecoder` 而非 `MultiGzDecoder`（上游对 gzip 也只用一个 zlib 解压器）；bzip2 的 `BzDecoder` 本就只读第一个流。三者均已用 Python 3.11 的 `r|*` 实测：成员被截断在第一个流末尾时报 `unexpected end of data`。`lzma-rust2` 固定在 0.15，这是仍依赖 `sha2` 0.10 的最新版本，避免与工作区并存两份 `sha2`。Rust 仍以 `Vec<u8>` 收归档；压缩 tar 通过校验后，所需的解码结果仍整段暂存，大小受限额约束，随既有归档流式化一起优化。pax 扩展头与 GNU 长名条目的内容由 `tar` crate 整段读入且不计入限额，与上游 `tarfile` 相同，未另加上限。zip 读取当前启用 deflate、bzip2、lzma；其他压缩方法由 reader 报错。`hydrate_workspace` 的内部快照 tar 路径当时未改；后随 P3 收尾按上游 `r:*` 支持三种压缩与多流（§3.21）。

新增 zip 成功、危险路径、解压限额、实际内容超过声明大小（stored／deflate），Unix 与 DOS 生成的链接成员、链接兼越界成员的拒绝原因，zip 重复路径（规范化后同名、文件与目录同名、原始同名）与两种顺序下穿过文件的路径，重复目录的成员数／累计大小及恰好达到限额、被覆盖的链接属性、ZIP64 大小、CP437 名称与根条目跳过，名称在 NUL 处截断（含截断后同名）与标了 UTF-8 却非法的名称，真实 unix-local session，三种压缩 tar，拒绝跨多个串接 xz 流或 gzip 成员才能补齐的 tar（保留归档本体、成员不落盘），压缩 tar 超限，以及只解码到成员结束处的测试。`it-sandbox` 全套、`ra-core`／`ra-sandbox` clippy、格式检查与分层检查通过。`ra-core`／`ra-sandbox` 的 Windows GNU 目标检查（含测试目标）在本机无 `x86_64-w64-mingw32-gcc` 的情况下通过；全工作区检查仍卡在 `ra-model`／`ra-eval`／`ra-cli` 引入的 `ring`，与归档无关。运行期排除路径、shell tar 参数、remote snapshot IO 与 Linux 指纹成功分支仍分别依赖 P8/P9、P1 和 Linux 环境。

### 3.15 R8-P1 第一批：session 作用域依赖与 pre-stop 回调（2026-09-23）

交付面：

| Rust | 上游 | 说明 |
| --- | --- | --- |
| `ra-core::sandbox::Dependencies` | `session/dependencies.py::Dependencies` | 值绑定与工厂绑定；`cache`／`overwrite`／`owns_result` 三个选项及默认值（缓存开、不覆盖、不持有）；`with_values`；`get`／`require`，缺失时报错信息带 key 与 consumer；重新绑定时中止旧绑定仍在运行的工厂，其等待方得到 rebound 错误；`close` 先中止并等完所有运行中的工厂，再按产生顺序的逆序、按对象身份去重关闭 owned 结果，幂等，调用方中途放弃等待时仍继续执行；值绑定从不关闭 |

Rust 表达差异（每条注明必要性）：

- **工厂与关闭都以 `tokio::spawn` 的任务执行**，ra-core 因此首次直接依赖 tokio（项目结构文档允许 ra-core 依赖 tokio）。上游靠 `asyncio.create_task` 与 `shield` 做到三件事：缓存工厂不随某个等待方取消而停止；重新绑定与关闭能中止没人在轮询的工厂；`aclose` 在调用方取消后继续执行。借用调用方 future 的实现做不到任何一件。无缓存工厂对应上游 `shield=False`：唯一的等待方放弃时中止该工厂。
- **任务要登记到真正结束为止**：Rust 的 abort 只是请求，另一个线程上正在进行的 poll 会先跑完，期间仍可能产出 owned 结果。所以任务由自身内部的 guard 在真正结束时注销，正常返回、panic、被中止都一样；重新绑定和无缓存工厂的放弃只发出 abort，任务在此之前一直留在 `active` 里，`close` 会等它结束并关闭它产出的东西。同一个 guard 也负责清理 `pending`，所以 panic 过的缓存工厂下次解析会重新运行，和上游 `_factory_task_done` 在任何结束方式下都移除 pending 一致。
- **值与关闭能力**：`DependencyValue` 包一个 `Arc<dyn Any + Send + Sync>`，取用时按类型 `require_as::<T>`；可关闭能力由 `CloseDependency` trait 显式声明，取代上游对 `aclose`／`close` 方法的鸭子类型探测，关闭仍是尽力而为。`with_closer` 允许取用的值和负责关闭的对象分开（例如按 trait 对象取用、关闭具体对象）；去重按关闭对象本身计，对应上游按 `id(value)` 只关一次。上游 `require` 把值为 `None` 的绑定当作缺失，Rust 的值不可能为空，这条分支不存在。
- **命名与参数**：关键字参数改为 `FactoryOptions` builder（`with_cache`／`with_overwrite`／`with_owns_result`，默认值不变）；`clone()` 命名为 `clone_bindings()`、`aclose()` 命名为 `close()`，避免与 Rust 的 `Clone` 语义混淆；缺失依赖提示里上游的 "pass it as `dependencies=`" 改写为 Rust 语境。三类异常合并为 `#[non_exhaustive]` 的 `DependenciesError`，`is_binding_error()` 对应 `DependenciesBindingError`。
- **session 侧**：trait 没有字段，所以新增必须实现的 `resources()`，每个后端内嵌一个 `SessionResources`。上游 `run_pre_stop_hooks` 用 `except BaseException` 连取消一起捕获并记为失败；Rust 的取消是 future 被丢弃，回调在开始前已标记为"已运行"，所以运行期间有一个 guard，未跑完就被丢弃时记下失败，下一次关闭因而不会跳过回调去持久化。原先的 `begin_close`／`end_close`（发现正在关闭就直接返回）不是上游语义，已删除；现在与上游一样，第二次关闭等前一次结束后完整执行一遍。
- **RemoteSnapshot 的 `restorable`**：上游不包装异常，让查找失败和客户端失败原样抛出；Rust 必须给出带错误码的 `SandboxError`，依赖缺失或类型不符报 `SandboxConfigInvalid`，客户端 `exists` 失败报 `SnapshotRestoreError` 并在 `reason` 里保留原信息。`RemoteSnapshotClient::exists` 有默认实现，报 "must implement `exists`"，对应上游客户端缺 `exists` 时仍能上传下载、只有询问会失败。客户端以 trait 对象取用，本身持有资源的客户端用 `closable_remote_snapshot_client_dependency` 打包，owns_result 的工厂产出它时关闭能力不丢。

Rust 表达差异（每条注明必要性）：

- **来源判定是结构性的。** 上游用闭合表 ＋ 类的 `__module__`／`__qualname__` 防止自定义子类冒充可信边界。这里内置策略是枚举变体：`MountProvider::Extension` 即自定义 mount，`MountStrategy::Extension` 即自定义策略；另外，一个只是**名叫**内置挂载类型的扩展条目视为伪造（对应上游"规范类的子类"被拒），在边界、脱敏与确认三处都拒绝。Pattern 是闭合枚举，不存在"自定义 pattern"，上游那一类检查无对应物。
- **托管后端的行不在表里。** modal／daytona／e2b／runloop／vercel／blaxel／cloudflare 的策略与 blaxel 扩展挂载所属后端均未移植；持久化载荷中出现它们按"未知类型"拒绝，blaxel 的 s3fs 分隔符检查随之缺席。各自随后端补入表中，不改判定逻辑。
- **`sanitize_manifest_mount_authority` 返回脱敏后的 JSON，不返回 typed manifest。** 上游 dump → 脱敏 → `model_validate`；Rust 回读需要宿主的三张注册表，而本批所有调用方（state 写出、拓扑比较）要的本来就是渲染。拓扑比较在两边的脱敏渲染上做，与上游比较重新校验后的 dump 等价。
- **读回入口按值收下载荷。** `SandboxSessionState::parse(payload: Value, snapshots, manifests)` 读完即丢，对应上游失败时 `payload.clear()`；所有失败统一为 `sandbox session state payload is invalid`，非对象为 `session state payload must be an object`（上游是另一种措辞的 `TypeError`）。`deserialize_session_state` 是带默认实现的 trait 方法（上游是抽象方法 ＋ helper），因为显式注册表必须由调用方传入；state 类型与后端不符报同一句 invalid，对应上游子类 `Literal` 类型校验失败。
- **`redact_mount_error_data*` 装饰器与"可信 owner"判定不移植。** `_call_has_configured_mount_authority`、`_exact_slot_state_entry`、异常图清理、`_replace_structured_sandbox_error` 处理的是 Python 异常帧保留局部变量、描述符可被劫持的问题；Rust 错误只携带放进去的东西，本模块所有错误文案与 context 只含字段名不含值。可观察的那部分——持久化载荷读失败不回显——在 `parse` 保留。挂载命令执行期的错误替换已随 P2 第三批在挂载生命周期边界移植（见 §3.20）。
- **脱敏失败的归类。** 上游写出时若 manifest 带权限，任何失败替换为 `MountConfigError("…could not be serialized")`，否则原样抛出 `ValueError`；Rust 两种都是 `MountConfigInvalid`（不带权限时保留原固定文案），渲染本身失败（如非 UTF-8 的文件内容）在不带权限时报 `SandboxConfigInvalid`。
- **修掉一个旧缺陷。** 原 `render` 用 `serde_json::to_value(&manifest).unwrap_or(Value::Null)`，渲染失败会被写成 `manifest: null`；现在失败即报错。
- **撤销一条自创规则。** 此前 `to_json` 拒绝带环境变量的 manifest，这不是上游行为；环境照上游直接写出。宿主来源的授权也照上游：state 自身渲染保留，客户端写出时丢弃，读回时无论是否有标记都剥离并记为待重绑定。
- `MountExposureError` 新增 `CustomMount`／`CustomStrategy`：上游在确认时抛 `MountConfigError`，Rust 的确认方法本来返回 `MountExposureError`，文案逐字相同。
- 来源检查遍历声明树而不经 `iter_entries` 的路径校验；路径错误由随后的 `mount_targets` 报出，只影响两个错误同时存在时先报哪个。
- `rebind_persisted_*`／`assert_path_grants_rebound` 里上游的 `ValueError` 映射为 `SandboxConfigInvalid`（op `start`），文案保留上游提到 `Runner`／`SandboxRunConfig.manifest` 的原话，P4 移植后名字一致。
- 空集合仍省略（§3.8 既有取舍），所以写出的 state 里被丢弃的 `extra_path_grants` 不出现，而不是 `[]`。
- `_sanitize_persisted_provider_identity` 钩子未加：上游只有 docker 覆写，随 P8。

接线：

- unix-local 的 client 与 session 新增 `with_mount_lifecycle`。`delete` 按上游逐个 `unmount` 临时挂载，有一个失败就保留根目录；挂载路径解析失败时同样保留（上游在这里会直接抛出）。

Rust 表达差异（每条注明必要性）：

- **行为由 lifecycle 提供，不挂在策略数据上。** Rust 的 strategy 是枚举数据，宿主注册的策略解析为 `MountStrategy::Extension`，没有地方挂行为；上游是子类自带方法。宿主实现 `MountLifecycle`，其余委托给 builtin。策略仍作为参数单独传入，保留上游"后端可以换一个策略来跑"的形状，激活边界查的也是实际要跑的那个。
- **取消语义用独立任务实现。** 上游用 `shield` 保护每次 transition；Rust 丢弃 future 时无法等待，所以整个序列跑在自己的 Tokio 任务里，调用方的 future 丢弃即通知该任务。可观察的差异只有一处：上游取消后仍向调用方抛出 teardown／remount 失败，Rust 没有人接收，改为 `tracing::warn`。所以上游 `…_settles_ambiguous_shutdown_after_cancellation` 断言的 `WorkspaceArchiveReadError` 在 Rust 无法断言，对应测试只断言 shutdown 跑完且只跑一次。
- **取消与结果同时就绪时，取消不会丢。** 独立任务用 `select!` 同时等 transition（或操作）与"调用方已离开"，两边同时就绪时先取结果；所以每次 transition 和操作结束后，都会再非阻塞地检查一次调用方是否已离开。这样，已离开的调用方不会让操作开始；即使设了 `restore_on_success=false`，也照样装回——已经没人能再装回它。上游 asyncio 的取消在下一个 await 点送达，没有这个窗口。
- **panic 与异常同样先清理再传播。** 上游捕获 `BaseException`，先装回、再重新抛出。Rust 用 `catch_unwind` 包住操作和每次 transition：panic 按该步失败处理，已卸下的装回，状态不明时终止会话，之后 `resume_unwind`，原本要返回的错误记日志。只在 unwind 模式下成立，`panic = "abort"` 时 panic 之后什么都不会运行。
- **transition 自身被取消的分支不移植。** 上游 `reason=mount_teardown_cancelled`／`mount_restore_cancelled` 对应 transition 协程里抛出 `CancelledError`；Rust 的 transition 总会被等到完成，没有单独取消的途径，该分支不可达。
- **`workspace_archive_error_summary` 的 `cause_type`。** 上游写 Python 异常类名。Rust 对 sandbox 错误写它的 error code 字符串；cause 不是 sandbox 错误时不写这个字段，因为 Rust 拿不到类型名。
- **运行期跳过路径指向工作区根时报 `SandboxConfigInvalid`**（op `persist_workspace`）；上游是 `ValueError`，没有错误码。
- `base_dir` 参数保留，但两个 builtin 策略都不读，与上游一致。
- 未移植：`current_task_owns_mount_transition`（基于 ContextVar，只有托管后端 cloudflare／modal／vercel 用）；`supports_native_snapshot_detach`／`_native_snapshot_requires_tar_fallback`（只有托管后端的原生快照路径用）。这两项随各自后端。`_redact_mount_lifecycle_error` 按 §3.16 的裁定不移植。

四种 pattern 的命令（均先查工具，缺了报 `MountMissingTool`）：

- **Mountpoint**：凭据写进每会话目录 `.sandbox-mountpoint-env/<hex>/<sha256[:16]>.env`（owner-only），命令行里 `source` 它；带内联凭据的 endpoint 经 `OPENAI_AGENTS_MOUNT_ENDPOINT_URL` 传。失败时 stderr 追加读回的 stderr 文件，命令与 stderr 中每个敏感值（含 URL 的 user／password／query 及其解码）替换为 `REDACTED`，并标记为已脱敏。
- **blobfuse**：YAML 逐行照移（缓存大小 0 与未设同样取类型默认，`attr_cache` 超时 0 保留），缓存目录不得落在挂载路径内，缓存与配置目录登记为快照排除。失败标记已脱敏。
- **rclone**：生成的配置总是单独一个 owner-only 文件；fuse 模式 `rclone mount … --daemon`，nfs 模式先起 `rclone serve nfs … &` 再 `mount -t nfs` 重试三次。卸载后 `pkill` 该 remote 的进程。
- **S3 Files**：`mount -t s3files -o <options> <fs>[:<subpath>] <path>`。

**边界错误替换**：内置 lifecycle 的四个方法、trait 提供的 `apply`／`unmount`，以及 `apply_pattern`／`unapply_pattern`，在返回错误前检查：错误已标记脱敏、挂载带有或可能藏有凭据、或会话 manifest 带挂载凭据——任一成立就替换。凭据边界的校验错误（边界、来源、重绑定拓扑）标记为"安全文案＋已脱敏"：直接调用这些校验函数时 context 照旧可见（P1 的测试不变），经过生命周期边界时被清空、文案保留，与上游一致。

Rust 表达差异（每条注明必要性）：

- **错误替换只落在挂载生命周期边界。** 上游同一个装饰器还挂在 `exec`、`shutdown`、`aclose`、client 的 `create`／`resume` 等会话方法上，而且会遍历 `self` 找 manifest 里的凭据，于是一个带凭据挂载的会话里，任何 exec 失败都会被替换。Rust 这层会话装饰属于 P9 的 instrumentation 包装，P1 已裁定不移植帧清理；本批只移植挂载操作本身的替换，会话方法保持原样。
- **pattern 配置不算凭据持有者。** 上游边界遍历参数时，dataclass 形式的 pattern 配置不在可信 owner 列表里，因此 pattern 边界只看"已标记"与会话 manifest，生命周期边界再加上 mount 本身。Rust 照此区分。
- **保留上游 shell 选择。** mount-s3、blobfuse2、mount.s3files 的工具探测通过 session 默认 shell 执行，UnixLocal 因此使用 `sh -c`；仅在上游明确指定时下发 `["sh","-lc",script]`，包括 rclone 与 timeout 的探测。
- **目录由会话的 `mkdir` 建，而不是命令。** 上游测试会话的 `mkdir` 是跑 `mkdir -p`，所以它的命令列表里有这两条；Rust 的 `SandboxSession::mkdir` 是独立操作，测试另行断言目录。
- **生成文件以规范化后的绝对路径写入。** 上游 `write` 收相对路径、内部再规范化；这里先经 `validate_path_access` 规范化再写，落点相同。
- **S3 Files 的 `extra_options` 按键名排序。** ra-core 的声明面用 `BTreeMap`（§3.8 既有取舍），多个额外选项的先后与上游插入序不同；pattern 自己追加的 `ro`／`mounttargetip`／`accesspoint`／`region` 仍在其后、顺序照移。
- **`_require_mount_config` 的类型名**：报 `expected`／`actual` 时用上游 dataclass 的类名字符串，便于两边对照。
- **NFS 客户端探测失败只记 `tracing::warn`**，对应上游 `warnings.warn`。
- **事件流脱敏不在本批。** `test_s3_mountpoint_failure_redacts_credentials_from_errors_and_events` 的事件那一半依赖 `SandboxSession` instrumentation（P9）；错误与命令那一半已断言。

**修正与偏离**：

- **`hydrate_workspace` 改为照移 `safe_extract_tarfile`。** 此前是 §3.9 自写的一份校验，拒绝理由是自拟的（`path_escapes_root`、`symlink_target_escapes_root`、`parent_is_symlink`、`unsupported_member_kind`），且缺三条规则。现在逐条对应上游 `validate_tarfile(allow_symlinks=True, allow_external_symlink_targets=False)` 与 `safe_extract_tarfile`：`reason`／`member` 用上游原文（`absolute path`、`parent traversal`、`hardlink member not allowed`、`absolute symlink target not allowed: …`、`symlink target escapes archive root: …`、`duplicate archive path: …`、`archive path descends through symlink: …`、`archive path descends through non-directory: …`、`windows drive path`、`windows path separator`、`path escapes root after resolution`、`symlink in parent path`、`destination directory already exists: …`）；补上**重复路径**、**穿过非目录**、**Windows 盘符与反斜杠**三条规则；目录成员遇到同名文件或链接时先删掉再建目录（`_prepare_directory_leaf`，原先直接失败）；**符号链接最后创建**；文件以 `O_EXCL|O_NOFOLLOW`、`0600` 创建，写完再 `fchmod` 到还原后的权限。输入按魔数识别 gzip／bzip2／xz 后解压，并且**读完所有流**：上游 `r:*` 模式的 `GzipFile`／`BZ2File`／`LZMAFile` 都会继续读后续成员或流（Python 3.11 实测：前后两半分别压缩的 tar 在三种格式下都能读出两个成员）；这和 `extract` 所用的 `r|*` 流式读取只读第一个流相反（§3.14）。老式 `\0` 类型且名字以 `/` 结尾的成员按目录处理，PAX 全局头按后续审核修复记录继承其属性，不作为文件成员提取。§3.13 记的"成员路径规则有两份实现"：两份的规则与理由文案现已一致，代码仍分两处（一份宿主侧直接写盘，一份经 session API），没有合并。
- **`read(user=…)` 的存在性探针照移，但传给它的是绝对路径——这是对上游的有意偏离。** 探针脚本 `READ_PATH_PROBE_V3` 逐字节照移，上下文键 `command`／`stdout_bytes`／`stderr`（按字符截到 4096 并加 `…`）／`existence_probe_exit_code`／`existence_probe_stdout_bytes`／`existence_probe_stderr` 照移，"访问检查退出码不是 1 就不探测、直接报读取失败"的分支照移（此前一律探测，且探针是自写的 `[ -e ]`）。偏离在于：上游探针与其他命令走同一个 exec，而本后端的 exec 会把工作区内的绝对路径改写成相对路径，探针又把相对路径当作从 `/` 起算来解析，于是**存在但不可读的文件被报成不存在**。已在基线 commit 的上游代码上用同一个替身 `sudo` 实测：权限 `000` 的 `locked.txt` 得到 `WorkspaceReadNotFoundError`、`existence_probe_exit_code=1`，记录到的探针参数是 `locked.txt`。探针是为不改写参数的远端后端写的；这里只让探针这一条命令不经改写（`exec::ArgumentPaths::AsWritten`），其余命令照旧改写。
- **挂载卸载失败的告警不再带挂载路径与错误。** 上游经 `log_tool_action_warning` 记录，默认 `DONT_LOG_TOOL_DATA=True`，只留固定文案，不带异常与诊断上下文，测试用 `SECRET_…` 名字钉住这一点。Rust 原先总是带 `mount_path` 与 `error`。现在两条告警（卸载失败、挂载路径无法解析）都只留文案。上游可用 `OPENAI_AGENTS_DONT_LOG_TOOL_DATA=0` 打开诊断，这个开关在 Rust 没有对应物，**未移植**；它属于框架级日志策略，不是沙箱的一部分。
- **macOS 围栏改为可按输入计算的值。** `HostConfinement`（`ra-sandbox::unix_local`，私有字段）持有上游每次执行时读取的三个输入：`sandbox-exec` 在不在、宿主 `PATH`、宿主 home。`current()` 按平台取当前宿主的值，session 只用它；**没有任何入口能给 session 换一个更弱的围栏**。profile 构造从"仅 macOS 编译"改为所有 unix 都编译，与上游一样由运行时决定用不用，所以 profile 的规则在 Linux CI 上也能验证。附带修正：`unix_local_confinement_unavailable` 的 `platform` 上下文改为上游的 `darwin`（原为 Rust 的 `macos`）。这与 §3.9 公开 `prepare_exec_command` 是同一个理由：上游的测试靠 monkeypatch，Rust 靠一个可以构造的值。

**用替身 `sudo` 首次端到端跑通"以另一账号操作"。** §3.9 记录过这一段"没有实测记录"。本批在 manifest 的 `PATH` 前放一个替身 `sudo`：它把收到的参数（NUL 分隔）逐次记下，然后以当前账号执行剩余命令。session 与进程之间的 shell 前缀、工作区相对改写、macOS 围栏都是真实的，替身记录的就是真 `sudo` 会收到的参数。上游录制子类记录的是改写**之前**的命令，所以上游断言绝对路径，这里断言的是改写后的相对路径。

**宿主环境类用例在子进程里跑。** 这些用例需要进程本身带着特定变量（`OPENAI_API_KEY`、`LC_MESSAGES`、`LC_PRIVATE_TOKEN`、`TMPDIR`），测试不能给自己的进程加变量而不与其他测试竞争。做法是 `#[ignore]` 的场景由父测试以子进程重新启动本二进制运行，环境变量只加在子进程上。父测试断言子进程恰好跑了 1 个用例；在缺少变量的环境里单独跑场景会失败（已实测）。

### 3.22 Unix-local 归档恢复审核修复（2026-09-24）

修复 §3.21 审核发现的两处归档读取偏差：

- **PAX 全局属性必须继承，不能直接跳过。** 对照 Python `tarfile.TarInfo._proc_pax`／`_apply_pax_info`，全局属性作用于后续成员，局部属性只覆盖当前成员，后续全局头更新继承值。Rust `tar` crate 不自动继承全局属性，因此读取扩展记录后，将有效属性作为单个局部 PAX 头交给其成员读取器；`path`、`linkpath` 在安全校验前生效，`size` 在读取载荷前生效。校验和、GNU 稀疏载荷仍由 `tar` crate 处理；缺少后续成员的扩展头报读取错误。
- **文件名与链接目标保留原始 Unix 字节。** 实际路径和安全校验使用 `PathBuf`／`OsStr` 字节，只有错误诊断使用有损字符串。对应 Python 的 surrogate-escape 路径语义：宿主支持该名称时原样恢复，不支持时返回文件系统错误，不再替换成 `�` 后写入其他名称。没有增加“必须 UTF-8”的限制。

新增 10 个回归用例：全局路径继承、局部覆盖不泄漏与后续全局更新；全局链接目标及其越界拒绝；全局路径越界拒绝；全局／局部 size 的载荷边界；非 UTF-8 文件名保护原有合法名称；非 UTF-8 链接目标原样保留；GNU 长名称／长链接与后续成员；GNU 稀疏载荷与后续成员；局部／全局 PAX 孤立扩展头两例。非 UTF-8 测试按实际文件系统是否支持字节名称验证成功或错误两条分支。

两条行为另用 Python 3.11 的 `tarfile`（`r:*`）实测对照：全局 `path` 被后续成员继承、局部 `path` 只作用于紧随的成员、后续全局头更新继承值；局部或全局扩展头之后没有成员时报 `ReadError`。

**同批修正一条偶发失败的日志用例。** `a_failed_unmount_is_logged_without_the_mount_path_or_the_error` 与同二进制里的删除用例并发时偶发捕获不到任何日志（单独运行 40 次全过，与整个二进制混跑时 8 次里失败 2 次）：`tracing` 的 callsite 兴趣缓存是进程级的，另一个线程在没有订阅者时先触达同一个 `warn!`，会把它缓存成"不关心"。该用例移到独立二进制 `unix_local_delete_logging`，连跑 30 次、`unix_local_client` 连跑 10 次均无失败；被测行为不变。

验证：macOS 上 `it-sandbox` 全部 22 个测试二进制 402 项通过、4 个子进程场景按设计 ignored；`ra-sandbox` clippy（全部目标，`-D warnings`）、两处修改 Rust 文件的 `rustfmt --check` 和 `git diff --check` 通过。Linux 分支未在本机实测。

### 3.23 R8-P4 第一批：SandboxAgent、SandboxRunConfig 与 runner 接线（2026-09-24）

移植 `run_config.py::SandboxRunConfig`、`sandbox/sandbox_agent.py::SandboxAgent`、`sandbox/runtime.py::SandboxRuntime`、`sandbox/runtime_agent_preparation.py` 与 `sandbox/runtime_session_manager.py::SandboxRuntimeSessionManager`，并接进 runner 的普通与流式两条入口（两者共用一个 loop，接一处即两处生效）。本地最小执行已经跑通：真实 unix-local 后端上，创建 → 物化 manifest → capability 工具经绑定的 session 写文件 → stop 持久化 snapshot → delete → 从 `RunState` 的 JSON 恢复 → 还原 snapshot → 读回文件。

**落点**（与 §8 裁决一致，`ra-runtime` 仍只依赖 `ra-core`）：

- `ra-core::sandbox::agent`：`SandboxAgentConfig`（`default_manifest`／`base_instructions`／`capabilities`／`run_as` 四个字段），以**组合**方式挂在 `AgentSpec::sandbox()` 上——带它的就是 sandbox agent；上游的 `_sandbox_concurrency_guard` 改为 `acquire_run` 返回的租约，drop 即释放。`process_manifest`／`manifest_with_run_as_user` 放在 core，因为要读 `Manifest` 的私有凭据确认策略（上游 `_merge_mount_credential_exposure_policy`）。
- `ra-core::capability::Capability` 补 `process_manifest` 与 `bind_sandbox(&SandboxBinding)`。上游的 `bind`／`bind_run_as`／`bind_workspace_scope` 三步合为一次调用并返回绑定后的新值（与既有 `bind` 的偏离同理：capability 以 `Arc` 共享、不可变，不需要每 run 深拷）；上游 `instructions(manifest)` 的 manifest 改由 `SandboxBinding::manifest()` 提供，方法签名在两条安装路径上保持一致。此前该 trait 文档写"没有 `process_manifest`，等 sandbox 落地再定形状"，本批兑现。
- `ra-core::sandbox::remote_mount_policy`：上游 73 行整体移植，措辞逐字（模型读到的文本）。
- `SandboxSession` 协议补：`set_concurrency_limits`／`set_archive_limits`（存于 `SessionResources`，与上游基类字段对应，所有后端免实现）、`replace_manifest`（上游直接给 `session.state` 赋值；这里 state 在后端锁后面，默认拒绝）、`apply_manifest_entries`（上游 `_apply_entry_batch`）、`validate_manifest_application`（上游同名，默认跑凭据边界）。`extract` 未指定限额时改用 session 的限额（上游 `self._archive_limits`）。
- `RunState` 增加 sandbox 恢复载荷（`sandbox_resume_state`），schema 升到 **v5**，理由写在版本摘要里：旧运行时把它当未知字段保留，但无法据此恢复，会给 sandbox agent 新建工作区。载荷在 setter、反序列化、序列化三处都经 `sanitize_run_state_sandbox_mount_authority`（移植上游同名函数与信封形状校验，新放在 `ra-core::sandbox::mount_security`），任何入口进来的挂载凭据都不会写进 checkpoint；形状不对的信封按上游文案拒绝、不回显内容，setter 拒绝时清空载荷（上游同样清空）。判定自定义条目是否注册用内建注册表：checkpoint 读入时还不知道宿主的注册表，所以"像挂载"的未注册条目在此被拒，其余自定义条目原样交给 client。
- `ra-runtime::sandbox`：`SandboxRunConfig` 九个字段照上游（`client`／`options`／`session`／`session_state`／`manifest`／`snapshot`／`concurrency_limits`／`archive_limits` 默认 **None**／`cwd`），另加一项 Rust 侧必需：读 checkpoint 所用的注册表（默认内建族）。session manager、agent 准备、runtime 门面为 crate 内部实现。
- `SandboxClient::default_snapshot_spec`：未配置 snapshot 时新 session 的快照去处（见"有意偏离"），core 默认 noop。
- `ra-sandbox`：unix-local 实现 `replace_manifest`／`apply_manifest_entries`／`default_snapshot_spec`（上游默认快照目录，`resolve_current_default_local_snapshot_spec`），并发限额改存 `SessionResources`。

**逐项照移的行为**：

- 选择优先级：live `session` → 当前 agent 在 checkpoint 里的条目（覆盖显式 state）→ 显式 `session_state` → 新建。"checkpoint 存在"不等于"当前 agent 有条目"：只认识别的 agent 的 checkpoint 会让当前 agent 退回显式 state。checkpoint 的 `backend_id` 与 client 不符即拒绝。
- 所有权：外部 session 为 borrowed，已运行则不 start、未运行则 start，永不 stop／shutdown／delete；run 创建或恢复的为 owned，首次使用必 start（即使后端报告 running）。清理顺序 pre-stop → （回调未失败才）stop → shutdown → delete → dependency close，每步都尝试，报第一个错误；多个 agent 逐个清理，全部成功才写新的恢复载荷，失败则载荷为空；run 的认领无论成败都释放。
- runner 层：清理失败只记 warning，不把已成功的结果改成失败（普通与流式同）；失败或取消的 run 同样清理，**且清理在独立 task 上执行**：流被丢弃时 reaper 给 run 的 `DRAIN_GRACE` 到期后会 abort run task，而 stop（持久化工作区）可能比这更久；清理跑在 run task 里会在 stop 与 delete 之间被截断。现在 abort 截不断它，reaper 在 run task 结束（自行结束或被 abort）后等清理完成，run 还没走到清理时由 reaper 发起，不设时限。非流式 `Runner::run` 的 future 被调用方中途丢弃时同理：future 被丢弃无法再 await，由一个 drop 守卫把清理交给独立 task（审核未提，同一类问题一并处理）。上游 Python 的 `finally` 在任务取消时照样 await 清理，这是对应的 Rust 形态；阻塞型输入 guardrail 在准备之前跑，触发即不创建、不启动、不修改 session；每轮开头准备（handoff 进来的 sandbox agent 在其第一轮准备），准备结果按 session 缓存。
- 新建 session：manifest 取 run config 的、否则 agent 的默认值，有 manifest 或有 `run_as` 时经 capability 处理（先校验挂载来源、再加 run_as 用户、再按安装顺序交给各 capability，失败且 manifest 带凭据时替换为不引用内容的错误）；`options` 缺失且 client 不支持默认值、或类型与后端不符时按上游文案拒绝；client 改写 manifest 后补回 run_as 用户。
- 恢复：路径授权与挂载凭据不入库，一律从当前可信 manifest（run config 的，否则 agent 默认的）重绑定；缺可信 manifest 按上游文案拒绝。恢复的 state 同样经 capability 处理与 run_as。
- live session 的 manifest 修改：未运行时只替换 manifest，由 start 物化；运行中只接受新增与修改——删除条目、替换条目类型、改动或新增挂载、改 root／environment／users／groups、改宿主路径授权拓扑，均按上游原文拒绝；只写差量。
- 指令拼装：默认 base prompt（上游 `instructions/prompt.md`，MIT，逐字随 `ra-runtime` 分发）→ `# Agent instructions` → `# Sandbox capability instructions` → `# Sandbox remote mount policy` → `# Filesystem`（深度 3 的树、截断提示、cwd 六行说明，不列额外路径授权）。capability 依赖缺失按上游拒绝；工具追加在 agent 自有工具之后；采样参数按安装顺序折叠。
- `cwd`：配置时规范化；每次准备都在 session 上以 agent 的用户执行 `test -d`、`test -x`（不经 shell），失败按上游文案报错；新建 session 先物化再校验。

**有意偏离与理由**：

- **恢复条目按 `AgentId` 做键。** 上游按对象身份区分 agent，再用 `name#2` 后缀给同名 agent 造稳定键（`_build_agent_identity_keys_by_id`、`_allocate_unique_agent_identity`）。Rusty 的 agent 本来就有注册表保证唯一的 `AgentId`，直接用它做键，后缀分配无事可做；条目里照旧写 `agent_name`。
- **只读当前载荷形状。** 上游还读自己早期版本写的形状（按进程内对象 id 做键、没有条目表只按名字）；本框架从未写过这些形状。
- **拼好的指令放在哪里。** 上游不论来源都作为模型的 instructions。Rusty 静态文本进缓存前缀、生成文本进易变尾部；base 与 agent 自有指令都是静态时整段静态，任一是生成的则整段按相同顺序生成（落在生成指令该落的位置）。capability 片段一律在准备时解析一次，符合 `Capability::instructions` 的既有契约。
- **准备缓存没有 run_as 分支。** 上游在 agent 的 `run_as` 于两轮之间被改动时重建准备结果；Rusty 的配置不可变，缓存只以 session 为键。
- **默认快照由 client 回答，而不是 runtime 自己找目录。** 上游 runner 未配置 snapshot 时自己去宿主目录建本地快照、目录建不出来才退回 noop。找目录、建目录是文件系统操作，`ra-core` 与 `ra-runtime` 都不做 IO，`ra-runtime` 也不依赖 `ra-sandbox`，所以决策点放到宿主本来就要注入的 client 上：`SandboxClient::default_snapshot_spec`，runtime 遇到失败同样退回 noop。unix-local 实现为上游那个目录，于是最常见的装配 `SandboxRunConfig::new().with_client(UnixLocalSandboxClient::new())` 直接得到上游默认值，不需要额外装配。**残余差异**：第三方 client 不覆盖该方法时是 noop（上游对任何 client 都给本地快照）；trait 文档写明工作区不跨 session 保留的后端必须覆盖。审核指出初版（runtime 侧解析器、未装即 noop）会让默认装配跨 run 丢工作区，已按此修正并删去 `with_default_snapshot`。
- **沙箱错误统一投影为 `Error::Sandbox { kind: Setup }`，原 `SandboxError` 作为 source。** §3.5 当时说投影"等第一个调用方再定"，runtime 就是这个调用方；按码细分留给需要分支的宿主从 source 读取。
- **顺带修正一处存量缺陷**：恢复被批准的工具调用时，runner 此前在 public agent 的工具里查找，而 capability（run 级或 sandbox）贡献的工具只在 execution 实例上，恢复会报"工具已不存在"。改为在 execution 实例上查找（直连绑定两者相同，准备过的实例是超集）。新增的审批恢复测试最先暴露了它。

### 3.24 R8-P4 第二批：缺口测试与 `@redact_mount_error_data` 边界（2026-09-25）

补齐 §3.23 列出的缺口用例，并移植 `runtime_session_manager.py` 上的两处 `@redact_mount_error_data`：`SandboxRuntimeSessionManager.ensure_session` 与 `_SandboxSessionResources.cleanup`。

**落点**：

- `ra-runtime::sandbox::session_manager::ensure_session`：调用前判定这次调用是否持有挂载权限，取上游 `_call_has_configured_mount_authority` 在这个调用点实际读到的四处——run config 的 `manifest`、`session_state` 的 manifest、live `session` 当前 state 的 manifest、agent 的 `default_manifest`。checkpoint 不在其中：它在入口已脱敏，恢复时重绑的权限也取自上面这些 manifest。失败时按上游 `_replace_protected_mount_error` 分三路：沙箱错误在"持有权限或已被标记"时经 `replace_protected_mount_error` 替换（保留码、操作、可重试性）；非沙箱错误在持有权限时换成上游通用句 `sandbox operation failed while using a protected mount configuration`；`Error::Cancelled` 原样放行（对应上游保留不带值的进程控制异常）。
- `RunSession::cleanup`：以 session 当前 state 的 manifest 判定，失败在持有权限或已标记时替换。runner 对清理失败仍只记 warning，替换在日志里生效。
- `SessionManager::cleanup` 补上游同名 span `sandbox.cleanup_sessions`（`session_count`），挂在 `sandbox.cleanup` 之下。
- **`Capability::process_manifest` 改为就地编辑**：`fn process_manifest(&self, manifest: &mut Manifest) -> SandboxResult<()>`（原为按值传入、返回新 manifest）。上游 `_process_manifest` 在 capability 失败后检查的是被就地修改过的那份 manifest，所以 capability 自己加进去的凭据也算数（`test_session_manager_redacts_authority_added_before_capability_failure`）；按值传入时 manifest 随失败一起丢掉，包装层只能看到交出去之前的那份。改为 `&mut` 后交出前、失败后两份都查；构建新 manifest 的 capability 用 `*manifest = …` 覆盖，语义不变。这是公开 trait 签名变更，树内实现只有两处测试夹具。
- `ra-runtime::sandbox` 模块文档删去过时的一句（"信封整体脱敏不在这里"——第一批审核后已补），改记 session 包装层仍缺。

**有意偏离与理由**：

- **权限判定只读四个具名来源。** §3.16 裁定不移植装饰器的"可信 owner"判定与帧清理，本批移植的是它可观察的一面——哪些失败被替换、换成什么——与 §3.20 在挂载生命周期边界的做法一致。上游沿对象图按键名遍历（`_sandbox_config`→`session`→`state`→`manifest` 等），遇到读不到的 owner 或遍历异常即 fail closed。Rust 这里的来源是静态类型字段，直接读，不存在"读不到"的分支。遍历还会读 `_trusted_s3_mount_credentials`，它只出现在 Vercel 扩展后端（`extensions/sandbox/vercel/sandbox.py`），Rusty 没有该后端，不移植。
- **不做帧清理**（`del args, kwargs`、`discard_mount_source_exception`），沿用 §3.16 的裁定：Rust 错误值不携带调用帧。替换后的错误不带 source，原错误随之丢弃。

### 3.25 R8-P5 第一批：token 截断、PTY 协议辅助与 unix-local 终端（2026-09-26）

- `ra-sandbox::unix_local::pty`（新模块）＋ session 接线：`supports_pty()` 改为 `true`（P3 时有意报 `false`，理由是没有实现）；`pty_start` 与一次性 exec 走同一条塑形链（`prepare_exec_command` → 工作区相对参数 → `sh -c` 的 `cd` 前缀 → macOS 围栏），为此把 `exec::run` 里的后三步抽成 `host_command` 共用。进程表照移：随机 id、表满（64）时按"保护最近 8 个 → 最久未用且已退出 → 最久未用"剪除、≥60 告警、finalize 看到退出码即移除并终止、`pty_terminate_all` 清表并逐个终止；终止时仍在运行的整组 SIGKILL，终端的控制端交给独立线程关闭，stop／shutdown 的 after 钩子最多等 100 ms（上游 `_wait_for_fd_close_tasks`）。写入：非终端进程有输入即拒（`pty_stdin_unavailable`），终端写入后等 100 ms 再收集；`EIO`／`EBADF`／`EPIPE`／`ECONNRESET` 视为终端正在关闭、不报错。请求里的 `timeout_s` 与上游一样被忽略。
- 依赖：新增第三方 `portable-pty 0.9`（只在 unix 目标进 `ra-sandbox`）。内部依赖边不变——`xtask` 分层表里"PTY 复用 `ra-exec` 进程监管时再加边"的预告撤回，PTY 与一次性命令一样自起进程；`Rusty_Agent_Project_Structure.md` 的依赖图同步改。

**有意偏离与理由**：

- **子进程设置交给 `portable-pty`。** 上游 `_preexec` 在 fork 与 exec 之间做 `setsid`、`TIOCSCTTY`、把 SIGINT／SIGQUIT 复位为默认；Rust 里这一步只能写在 `pre_exec`（`unsafe`），而 workspace `unsafe_code = "forbid"`。`portable-pty` 的子进程设置覆盖上游三步，另外还复位 SIGCHLD／SIGHUP／SIGTERM／SIGALRM、清信号掩码、关闭多余描述符；codex 的 `utils/pty` 用的是同一 crate 同一版本。对命令可见的两处差别：环境里总会有 `SHELL`（该 crate 在 `env_clear` 之后仍写入），以及窗口大小为 0×0 以对齐上游 `os.openpty()` 不设大小。
- **终端退出码经标准库取得。** `portable-pty` 的退出状态只保留信号名、丢掉编号，信号结束的进程会报成 1；上游 `returncode` 是 `-signum`，`test_pty_terminal_signals_interrupt_even_if_parent_ignores_signal` 断言的就是它。这里把子进程句柄 downcast 回 `std::process::Child` 等待，退出码与一次性 exec 同一换算（信号取负）。
- **终端读取在阻塞线程上**（上游 `run_in_executor(os.read)`，同为线程），等待子进程也在独立线程上；二者都用 `std::thread` 而非 tokio 阻塞池，避免 runtime 关闭时被卡在读里的线程拖住。
- **非终端进程用独立进程组而非新 session。** 上游 `start_new_session=True`；新 session 同样只能在 `pre_exec` 里建。沿用 P3 一次性 exec 的同一替代（`process_group(0)`），整组终止语义不变，差别是子进程仍在宿主的 session 里。标准输入照上游继承宿主的。
- **终端写入写全部字节。** 上游一次 `os.write` 且不看写了多少，终端只收下一部分时余下的输入被静默丢掉；上游预期的输入短到一次写得完，这种情况下两者一致。写入放在阻塞线程上，因为不读输入的进程会让写入阻塞。
- **"stdin 不可用"是带专属 detail 的 `ExecTransportError`（不可重试）。** 上游抛的是沙箱错误体系之外的裸 `RuntimeError`，工具层按消息文本识别；Rust 的 session 协议只返回 `SandboxError`，于是借用最接近的码（进程在，通往它输入的通道不在），并用 `PtyStdinUnavailable` detail 供识别，消息原文保留。没有为它新增错误码——码表是上游的 33 个。
- **登记前取消会终止进程。** 起进程到登记进表之间有一次锁等待；调用 future 在那里被丢弃时，进程组会被杀掉而不是变成表外孤儿（上游 asyncio 同一窗口没有处理）。登记之后的取消与上游一致：进程留在表里，等 stop／shutdown 清理。

## 4. 运行集成

### 4.1 `SandboxRunConfig`（`run_config.py`）—— 九个字段

| 字段 | 默认 | 语义 |
| --- | --- | --- |
| `client` | None | 建/恢复 session 的客户端 |
| `options` | None | 建新 session 时的客户端特定选项 |
| `session` | None | **外部 live session 覆盖**（本进程内） |
| `session_state` | None | 不用 `RunState` 时的显式恢复来源 |
| `manifest` | None | 建新 session 的 manifest 覆盖 |
| `snapshot` | None | 建新 session 用的快照 |
| `concurrency_limits` | `SandboxConcurrencyLimits()` | 物化并发 |
| `archive_limits` | **None** | None＝不施加 SDK 归档限制；要默认值须显式传 `SandboxArchiveLimits()` |
| `cwd` | None | **模型可见的工作目录**，相对 workspace root |

`cwd` 的语义边界写得很死，必须原样移植：它**只改相对路径解析**，不限制 run、不阻止访问会话策略允许的其他路径、不改 `Manifest.root`、不改 `BaseSandboxSession` 的直接路径行为。内建的 `exec_command` / `view_image` / `apply_patch` 从它解析相对路径；自定义能力必须自己应用绑定的 `SandboxWorkspaceScope`。校验时目录必须存在且对配置用户可访问；新建 session 时 runner **先物化 manifest 再校验 cwd**。

两个限额类型：
- `SandboxConcurrencyLimits{manifest_entries, local_dir_files}`
- `SandboxArchiveLimits{max_input_bytes, max_extracted_bytes, max_members}`，`__post_init__` 即校验，全都 `>= 1` 或 None。

### 4.3 runtime 三件套

| 模块 | 职责 |
| --- | --- |
| `runtime.py::SandboxRuntime` | 面向 Runner 的门面：`enabled`、`current_session`、`prepare_agent`、`cleanup`、`apply_result_metadata`、`assert_agent_supported`，以及 memory 入队两个口子 |
| `runtime_agent_preparation.py` | 纯函数层：`clone_capabilities`、`prepare_sandbox_agent`、`prepare_sandbox_input`、`build_sandbox_instructions`、`resolve_instructions`、`resolve_sandbox_model_name`、`get_default_sandbox_instructions` |
| `runtime_session_manager.py::SandboxRuntimeSessionManager` | session 的建/恢复/清理与所有权：`acquire_agent`、`ensure_session`、`serialize_resume_state`、`cleanup`、`_create_resources` |

**所有权是这层的核心裁决**，`_SandboxSessionResources` 持 `owns_session: bool`：
- 外部传入的 live session → `owns_session=False`，资源 `cleanup` 直接返回，不停不删；`ensure_started` 才检查 `running()`，已运行则不重复 start，未运行则启动。manifest 的有限更新发生在资源准备阶段，不是 cleanup；
- client 创建或恢复出来的 → `owns_session=True`，由本层负责收尾。

还维护**按 agent 的资源与恢复身份**（`_resume_agent_base_key`、`_resume_state_payload_for_agent`），即一个 run 里多个 agent 各自有自己的 session 与恢复条目。

> 这一条直接否掉旧 R8-10 的「一个 run 一个容器、run 结束一律删」。

**选择优先级**（`_create_resources`）：先取显式 live `session`，此分支不创建／恢复；否则先取 `session_state`，若 `_resume_state_payload_for_agent` 返回当前 agent 对应的 RunState payload，则反序列化并覆盖显式 state，再标记持久化授权；有有效 state 则 resume，否则 create。不能把“整个 RunState 存在”当作“当前 agent 有可恢复条目”。fresh create 才检查 options 必填条件，允许默认 options 的 client 除外；resume 不走 fresh create 的 manifest/options 路径。live session 的 manifest 更新与 resume 的授权重绑定分别处理。

**运行资源清理**：按 agent 逐个尝试清理，即使前一个失败也继续处理其余；仅全部成功后序列化新的 resume state；最后清空运行内资源表并释放 agent guard。结果层对 cleanup 失败如何处理另按普通／流式路径测试，不能把资源 cleanup 抛错直接等同于整次成功结果被改成失败。

## 5. `Capability` 契约（`capabilities/capability.py`）

pydantic 模型，字段 `type`、`session`、`run_as`、`workspace_scope`（后三者 `exclude=True`，不进序列化）。

绑定三步：`bind(session)`、`bind_run_as(user)`、`bind_workspace_scope(scope)`。
克隆：`clone()` 逐字段深拷，但对 session/scope/锁/工具对象**故意不拷**（`_clone_capability_value` 白名单）。

六个可覆盖点：

| 方法 | 默认 | 用途 |
| --- | --- | --- |
| `required_capability_types()` | `set()` | 声明必须共存的能力 |
| `tools()` | `[]` | 贡献模型可见工具 |
| `process_manifest(manifest)` | 原样 | 改 manifest |
| `instructions(manifest)` | None | 追加确定性指令片段 |
| `sampling_params(params)` | `{}` | 追加模型请求参数 |
| `process_context(context)` | 原样 | 采样前改模型输入 |

默认集 `Capabilities.default()` = `[Filesystem(), Shell(), Compaction()]`。
- `Filesystem.tools()` → `[view_image, apply_patch]`
- `Shell.tools()` → `[exec_command]`，**仅当 `session.supports_pty()` 才追加 `write_stdin`**

## 8. Rust 模块与依赖落点（裁决）

保留 `xtask/src/layering.rs::ALLOWED_INTERNAL_DEPS` 的 `ra-runtime → ra-core` 约束。撤回 runtime 直接依赖同时包含后端的 `ra-sandbox` 提案；协议与具体后端分开，不能通过允许一条反向依赖把 exec、tools 和 Docker 间接带进运行内核。

| 落点 | 内部依赖／消费者 | 职责 |
| --- | --- | --- |
| `ra-core::sandbox`（新增模块） | 不增加内部 crate 依赖；由 runtime、工具和后端消费 | 上游中立的 client/session/capability 协议与共享值、错误、manifest/state 表达、snapshot/dependency 接口。runtime 需要的 SandboxAgent 配置使用组合表达；options/state 的后端扩展通过显式注册与类型擦除传递，不能用封闭的内置后端枚举堵住第三方 client。具体 Docker 字段和 IO 实现不放这里。 |
| `ra-sandbox`（拟新增服务 crate） | `ra-core`、`ra-exec`、`ra-tools`；产品装配层消费 | session 共用生命周期实现与装饰层、物化／snapshot／sinks 的具体 IO、Unix-local/Docker client，以及默认 capabilities 的具体实现。默认能力通过 ra-tools 创建绑定 session 的工具；对外提供其共享协议实现。 |
| `ra-tools::sandbox` | 新的 session 工具只依赖 `ra-core::sandbox` 协议；现有 exec/patch 依赖保留 | exec/write_stdin/patch/view_image 的上游工具形态与绑定；不依赖 ra-sandbox，避免 `ra-sandbox → ra-tools → ra-sandbox` 环。 |
| `ra-runtime` | **仍只依赖 ra-core** | RunConfig 的 sandbox 配置引用核心协议；运行资源选择、按 agent 的身份与 owned/borrowed、preparation/cleanup 调用注入的 client/session/capability。不能直接构造具体后端或工具。 |
| 产品／SDK 装配层 | 可依赖 ra-runtime、ra-sandbox；coding 产品继续依赖 ra-tools | 构造并注入客户端及默认 capability 实现、snapshot 工厂、后端注册表；提供构建 SandboxAgent 的便利入口，保持上游默认集与配置语义，不要求模型调用者手工凑三种能力。已有更严格配置单独选择。 |

**实际调用链**：装配层构造具体 client 与 capability 实例 → 经核心协议放进 sandbox agent/run 配置 → runtime 调用 client.create/resume 或使用 borrowed session → capability 绑定同一 session，产出核心 Tool 协议对象 → runtime 通过既有派发调用工具 → 工具调用 session 协议 → 后端执行。runtime 不需要知道实现在哪个 crate。

**Compaction 等跨章能力**：其共享协议先登记在核心，具体能力由服务层装配已有机制；需要其他服务依赖时在对应任务核对现有允许方向并补精确边，不允许反向依赖 runtime。未核对的实现细节仍列 §11，不据此另建 compaction 引擎。

**注册方式确定为宿主显式装配**；装配入口自动登记选用的内置实现，第三方实现可追加。保留上游类型判别、未知类型与重复登记错误，Rust 不照搬 Python 导入时副作用。P1 实现时同步登记新 crate 分层与允许边，必须验证无环和 runtime 仍仅依赖 core。本次仅裁决文档，不修改代码或放宽现有门禁。
